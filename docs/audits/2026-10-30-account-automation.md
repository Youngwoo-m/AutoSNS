## 1. 사용자 목표와 이번 단계

사용자 목표는 개인계정과 학과계정의 채널을 각각 자동 운영하는 것이다. 이번 단계는 현황 점검, 설계, 단계별 실행 계획 수립이다. 실제 발행·로그인·자동 작업 변경·운영 코드 구현은 포함하지 않는다.

설계할 최종 상태는 다음과 같다.

> 개인·학과가 각자의 채널, 콘텐츠, 인증, 일정, 발행량, 예산, 이력을 갖고 기획 → 작성·검토 → 이미지·영상 제작 → 예약·발행 → 공개 확인 → 성과 분석을 운영한다. 사람은 운영 정책과 인증·검토 예외를 처리한다.

교차 게시 정책은 사용자가 2026-10-30에 “현재 교차 게시 방식 유지”로 선택했다. 기존 경로와 동작을 보존한다. 자동 승인 범위의 변경은 아직 확정하지 않았다. 기존 운영의 승인 수준이나 게시 경로를 이 문서로 변경하지 않는다.

## 4. 인증과 계정 확인

- 실제 로그인 폴더는 `~/.autosns-login/dept`, `~/.autosns-login/personal` 두 개다. 서비스별 프로필 별칭은 동일 계정 잠금으로 합쳐진다(`common/shared/axlock.py:250`, `:270`).
- YouTube·Blogger·Search Console의 토큰 참조는 계정별로 나뉜다(`common/shared/token_store.py:20`). 비밀값을 열거나 갱신하지 않았다.
- 개인 YouTube 발행기는 업로드 전후 채널 ID를 확인한다(`geoai_short_post.py:57`, `:209`).
- 공통 발행 어댑터는 실행 인자 계정과 콘텐츠 메타데이터 계정의 일치를 직접 확인하지 않는다. Blogger는 `dept` 이외를 개인 분기로 처리한다(`publishers.py:67`, `:135`). 현재 호출 경로와 별개로 공통 계약에서 엄격한 검증이 필요하다.
- 기획 에이전트는 계정별 사이트를 조회하면서 Search Console 토큰은 개인 참조로 고정한다(`ax-console/app/agents/planner.py:25`).

사용자 결정은 **현재 교차 게시 방식 유지**다. 위 기존 경로를 폴더 분리나 실행 규칙 통일을 이유로 삭제하거나 축소하지 않는다. 현재 비활성인 작업을 켜거나 새 교차 게시 경로를 추가하는 승인으로 확대 해석하지 않는다.

설계 제안은 원본 소유 계정과 게시 대상 계정을 각각 기록하고, 기존 교차 게시를 명시적인 배포 작업으로 표현하는 것이다. 동작을 보존하기 위해 대상 계정·채널, 콘텐츠 변환, 시각·대기 간격, 중복 방지, 실패 처리의 기존 조건을 이행 전후 대조한다. 이 구현 방식 자체는 아직 사용자 선택·설계 승인 전이다.

## 6. 자동 작업 등록과 실행

점검 시 등록부는 37개(학과 15·개인 14·공통 8), `com.smuds.*.plist` 파일은 33개였다.

- 등록부에만 있는 이름: `cacheprune.daily`, `captionautofix.daily`, `claude.building-daily`, `claude.safety-daily`, `digest.daily`, `indexcheck.daily`, `tiktok.queue`.
- plist에만 있는 이름: `disastershorts.prevoice`, `friendnotify.hourly`, `maint.daily`.

이 차이는 이름 변경·삭제·미설치 등을 구분해 대조해야 한다. 곧바로 누락 작업을 켜거나 plist를 재생성하면 안 된다. plist 존재, `Disabled` 필드, launchctl의 비활성 설정, 현재 로드 상태, 최근 성공은 서로 다른 증거다. 이번 환경의 `launchctl list` 결과만으로 전체 작업이 내려갔다고 판단하지 않았다.

현재 구현된 기반:

- 작업 중복 잠금, 계정별 프로필 잠금, 40분 자원 대기, 비상 정지.
- 콘솔 예약 확인, 기획 제안, 초안·자체 검토·출처 검토 후 자동 승인·예약 경로.
- 10분 주기 감시와 설정에 따른 원인 분석.
- 기존 주간·월간 성과 보고서.

남은 차이:

- 잠금과 대기는 영속적인 작업 대기열·자동 재시도와 다르다.
- 콘솔 재시작 시 실행 중 작업을 실패로 돌리며 외부 게시 결과 확인 후 이어서 진행하는 공통 처리가 없다(`server.py:2170`).
- 일부 성공 판정은 종료코드나 발행 응답에 기대므로 예약·공개·검증 상태를 구별해야 한다(`server.py:1361`).
- 자동 승인 일일 한도는 계정별이 아닌 전체 자동 승인 집계다(`server.py:1206`).
- 대기 중 비상 정지가 켜지는 경우의 실행 직전 재확인도 수락시험에 포함해야 한다(`axlock.py:333`).

## 7. 최종 상태의 수락 기준 제안

| 기준 | 최종 검증에 필요한 증거 |
|---|---|
| 계정·대상 확인 | 모든 발행 경로가 계정·채널·대상 ID를 검증하며 불일치 시 게시 전 차단되는 시험 |
| 설정·데이터 소유권 | 개인 작업이 학과 기본 설정·프로필·산출물 경로로 묵시적으로 넘어가지 않는 확인 |
| 등록 정합성 | 작업 정의·스케줄·설치·로드·중지·최근 실행 상태를 대조한 목록 |
| 중복 없는 복구 | 요청 중단·타임아웃·응답 유실·재시작 후 기존 게시물을 조회하고 중복 생성하지 않는 시험 |
| 부분 성공 복구 | 다중 채널 중 실패한 대상만 재처리하고 성공한 채널은 유지하는 시험 |
| 공개 검증 | 콘텐츠·계정·채널·게시 ID·URL로 예약, 공개, 검증 상태가 연결되는 기록 |
| 정책 분리 | 계정·채널별 승인 수준·한도·예산·주제 정책이 독립적으로 적용되는 시험 |
| 교차 게시 | 허용한 경로만 대상 작업으로 생성되며 출발·도착 계정을 추적할 수 있는 기록 |
| 비상 정지 | 진입 전·대기 중 정지 시 새 게시가 시작되지 않고 정책대로 재개되는 시험 |
| 성과 순환 | 검증된 게시물별 성과가 원본 콘텐츠와 다음 기획으로 이어지는 기록 |

수락 기준은 목표의 제안이며, 현재 충족됐다는 판정이 아니다. 운영 대상 채널과 자동 승인 범위를 정한 뒤 설계에서 확정한다.

## 8. 비교할 설계 접근

| 접근 | 장점 | 비용·한계 |
|---|---|---|
| A. 계정 등록부·실행 컨텍스트부터 통일 | 기존 스크립트를 유지하면서 발행 경계를 먼저 검증 | 당분간 폴더와 코드 소유권이 일치하지 않음 |
| B. 공용 기능 추출·개인 코드와 데이터 이동부터 진행 | 최종 폴더와 소유권을 빨리 맞춤 | import·가상환경·절대경로·launchd를 동시에 다뤄야 함 |
| C. 개인·학과를 별도 프로젝트·서비스로 분리 | 배포·장애·권한 경계가 강함 | 제작·검토·잠금 기능 중복과 운영 부담 증가 |

사용자는 A(실행 규칙 통일 후 폴더 분리)를 선택했다. A로 실행 경계를 검증한 다음 폴더·데이터를 점진 이행한다. B를 첫 단계로 수행하거나 C로 별도 서비스를 만드는 방식은 채택하지 않았다. 상세 설계 문서는 별도 검토·승인 대상이다.

후보 진행 순서: 운영 등록부 정합성 → 실행·결과 규약 → 채널 어댑터 연결 → 계정별 폴더·데이터 이행 → 복구·승인 정책 → 성과 순환. 구체적인 파일별 구현 계획은 설계 승인 후 작성한다.

## 9. 설치한 확장 기능의 위치

`social`, `content-strategy` 스킬과 Metricool·vidIQ 플러그인은 이번 대화에서 설치됐다. 그러나 점검한 운영 코드에 Metricool·vidIQ 연동 지점은 확인되지 않았다. 대화에서 사용 가능한 도구와 launchd·Claude 자동 작업에서 호출할 수 있는 연동은 다르다. 자동 운영에 넣으려면 실행 환경의 인증·API·지원 채널·비용·결과 검증 경로를 별도로 확인해야 한다. 설계의 필수 의존성으로 미리 정하지 않는다.

## 10. 문서 정합성과 다음 결정

`docs/폴더지도.md`는 10월 21일 구조를, `docs/개인계정_이동안.md`는 일부 이미 반영된 이전을 미실행 제안으로 설명한다. `ax-console/docs/전체자동화_개발파이프라인.md`의 초기 현황도 현재 코드보다 오래됐다. 설계가 정해지면 현재 지도·운영 등록부·로드맵의 기준 문서를 정하고 기존 문서를 갱신해야 한다.

교차 게시 정책은 현재 방식 유지, 설계 접근은 A로 결정됐다. 상세 설계 문서를 작성·독립 검토해 사용자에게 제시하고, 설계 승인 후 단계별 실행 계획을 작성한다. 이번 단계에서는 운영 코드를 구현하거나 실제 발행하지 않는다.
