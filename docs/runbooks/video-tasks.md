# 저장한 숏츠 계획의 영상 작업

`VideoTaskStore`와 `VideoTaskService`는 원고 버전과 계획 버전을 고정해 영상 제작 상태를 보존한다. 기존 Remotion 제작기·자산 재사용 승인·미디어 검사 계약을 사용한다. 검사를 통과한 산출물을 등록해도 `review_status=not_checked`이며 사람의 최종 검토를 완료했다고 표시하지 않는다.

## 흐름

1. `create(content_id, expected_revision, expected_plan_revision)`는 소유 계정·현재 원고·계획·입력 준비를 검사하고 `queued`만 저장한다. 웹 요청에서 파일 복사나 렌더를 시작하지 않는다.
2. 신뢰된 실행기가 `run_next()`를 명시 호출하면 대기 한 건을 원자적으로 선택한다. 작업공간의 OS 파일 잠금으로 영상 제작기를 직렬 실행한다.
3. 실행 직전 원고와 계획을 다시 대조한 후 선택한 자산을 새 시도 폴더에 복사한다. 등록된 제작기와 검사기를 통과한 결과만 `rendered`로 먼저 저장한다.
4. 검증된 MP4를 결정적 파일명으로 새 원고 버전에 CAS 등록한다. 원고·변환본·출처·기존 자산은 보존한다.
5. 등록 직후 중단된 경우 `resume()`은 입력 버전+1, 기존 내용·자산, 추가 MP4의 해시·크기·바이트를 정확히 대조해 완료를 연결한다. 재렌더하거나 자산을 중복 추가하지 않는다.

같은 입력·계획 요청은 기존 작업을 반환한다. `preparing`, `rendering`, `unknown`은 자동으로 초기화하거나 재렌더하지 않는다. 렌더 예외나 불명확한 결과는 그대로 보존한다. 원고나 계획이 달라지면 `content_changed`로 보존하며 덮어쓰지 않는다.

## HTTP

로그인·요청 출처 검사를 적용한다. 브라우저가 파일 경로, 제작 명령, 소유 계정, 검사·승인 증거를 지정할 수 없다.

| 요청 | 용도 |
|---|---|
| `GET /api/v2/video/capabilities` | 서버에 주입한 제작 서비스의 활성 여부 |
| `GET /api/v2/contents/{id}/video-tasks?revision=N` | 버전별 저장 작업 |
| `POST /api/v2/contents/{id}/video-tasks` | 정확히 `expected_revision`, `expected_plan_revision`을 받아 대기열 등록 |
| `GET /api/v2/video-tasks/{task_id}` | 저장 상태 |
| `POST /api/v2/video-tasks/{task_id}/resume` | 빈 객체 `{}`로 이미 렌더된 결과의 등록만 재개 |

기본 서버는 제작 서비스를 주입하지 않는다. 작업 조회용 독립 SQLite만 명시 초기화한다. 서비스 주입 시 작업·콘텐츠·계획 저장소가 모두 같은 관리 작업공간인지 서버가 확인한다.

## 작업 화면

기존 네 메뉴를 유지하며 저장 원고 편집기의 숏츠 계획 아래에 접힌 **영상 제작** 패널을 둔다. 원고를 열면 기능 상태·저장된 계획·작업 목록을 GET으로 조회한다. **영상 제작 요청**은 저장한 원고와 계획의 버전만 전송하고, **영상 작업 다시 조회**는 조회만 한다. 자동 접수·폴링은 없다.

원문·음성·숏츠 계획 등 다른 편집 입력이 미저장이면 영상 접수를 막는다. 계획을 저장한 뒤 영상 패널에서 다시 조회하면 새 계획 버전을 읽는다. 조회 실패·접수 결과 불명확 시 기존 목록을 보존하고 전체 재조회가 성공할 때까지 변경 요청을 막는다. 진행 중 작업이나 `rendered` 결과 등록 대기가 있으면 새 제작 요청을 막는다. **결과 등록 재개**는 `rendered`에만 제공한다.

완료는 영상 생성·등록만 뜻한다. 편집 중인 원고를 자동 전환하지 않으며 **최신 버전 열기**로 새 MP4 자산을 확인한다. 검토 상태는 계속 `not_checked`다.

## 명시 기동과 종료

`VideoRegistration`은 서버 코드가 제공한 제작기 factory·재사용 승인자·실측기·영상 검사기 네 가지 callable을 묶는다. `build_video_task_service`는 같은 관리 저장소에 서비스를 조립할 뿐 이 구성요소를 실행하거나 저장소를 생성하지 않는다. 누락되거나 다른 저장소를 지정하면 거부한다.

`production_main.run(args, video_registration=등록객체)`에서 `--serve --enable-video`를 명시해야 활성화된다. `--enable-production`(텍스트), `--enable-voicebox`(음성)와 독립적이다. CLI 단독 호출에 신뢰 등록을 제공하지 않으면 `video_registration_required`로 거부한다. 웹·환경변수·설정 JSON의 임의 명령이나 검사 완료 플래그를 등록으로 바꾸지 않는다. `--check`와 기본 기동은 영상 worker를 실행하지 않는다.

`build_production_application`은 enabled 서비스를 명시 주입받았을 때만 영상 worker를 조립한다. 생성 단계에는 thread나 제작 호출이 없다. `serve_forever()`에서 영상 worker를 시작하며 텍스트 제작이 비활성이어도 영상 worker만 실행할 수 있다. 종료는 모든 worker에 정지를 먼저 알리고 같은 제한 시간 안에서 진행 중 작업을 기다린다. 진행 중 렌더를 강제 종료하지 않는다. 실패하면 HTTP를 종료하고 오류를 반환한다. 제한 시간에 끝나지 않으면 `video_worker_not_stopped`와 `stuck` 상태·claim을 보존하며 자동 재기동하지 않는다.

worker는 다음 작업을 가져오기 전에 정지와 enabled 정책을 확인한다. 다른 프로세스의 작업공간 잠금이 사용 중인 경우만 대기하며, 그 밖의 예상하지 못한 오류는 숨기지 않는다.

## 검증 범위와 남은 연결

가짜 제작기·검사기와 임시 저장소로 대기열·직렬 잠금·계정/버전 결속·입력 변경 거부·검사 누락 차단·한 번만 렌더·중단 후 중복 없는 등록을 시험했다. 실제 Remotion 렌더, 새 모델 호출, SNS 접속·발행은 하지 않았다.

개인·학과 각각 임시 HTTP application에서 접수→worker→기존 미디어 검사 계약→새 버전 등록→멱등 재요청→정상 종료를 확인했다. 제작 leaf·실측·검사기는 가짜이며 실제 미디어 품질 증거가 아니다. Python 회귀 188개, 화면 회귀 314개가 통과했다.

남은 필수 작업은 실제 템플릿·글꼴·재사용 승인·검사기를 신뢰 등록으로 제공하는 연결과 실제 입력·산출물의 품질 검증이다. 8769 운영 개발 기동에는 영상 서비스를 주입하지 않아 기본 비활성 상태를 유지한다.
