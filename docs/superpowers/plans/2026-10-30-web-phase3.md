# 운영 웹 3단계: 승인·배포 계획·교차 발행 미리보기

> 구현 방식은 사용자 지정 병렬 에이전트이며 `superpowers:subagent-driven-development`를 적용한다. 아래 공통 계약을 고정한 후 독립 파일을 나눈다.

**Goal:** 저장한 콘텐츠 버전을 대상 채널과 연결하고 승인·일정·교차 경로를 로컬 원장과 화면에서 관리한다.
**Architecture:** 별도 관리 저장소에만 v2 스키마를 추가한다. 서버 정의 등록부로 원본·대상·정책을 확정하며, 기존 운영 자료와 발행기는 관측 대상으로 유지한다. 저장된 계획과 원격 예약을 구분한다.
**Tech Stack:** 기존 Python/SQLite·buildless UI·unittest/Node. 외부 API·브라우저 발행·AI 호출 없음.
**Spec:** [확정 화면 §8](../specs/2026-10-30-account-web-screens-design.md), [승인 운영 설계](../specs/2026-10-30-account-channel-automation-design.md), [전체 실행 계획 T2~T6·T9](2026-10-30-account-channel-automation.md).

## 범위와 제약

- 화면 설계대로 3단계는 저장·미리보기·가짜 어댑터 시험까지다. 실제 원격 예약 생성·게시·재시도·프로필·토큰 갱신·워커·타이머·launchd 변경은 제공하지 않는다. 실행 권한은 모든 응답에서 `execution_enabled=false`다.
- 2단계 ContentStore/IntegrationStore 데이터와 기존 조회·편집 기능을 유지한다. 사용 선호의 connection_id를 발행 연결 ID로 사용하지 않는다. `enabled_preference=true`는 인증이나 승인·실행 활성 근거가 아니다.
- 실제 target ID·인증·실행기 지원·사용자 활성 상태를 분리한다. 미확인 ID는 null로 보존한다. 확인되지 않은 계정·연결을 개인 계정으로 대체하지 않는다.
- legacy 일정/실행/교차 게시 주인은 변경하지 않는다. 기존 경로는 `delivery_owner=legacy`로 남기며 새 managed 실행 요청을 만들지 않는다. 새 관리 콘텐츠에 대한 로컬 계획만 저장한다.
- 운영 source_root·자격증명·프로필 경로를 응답에 내보내지 않는다. 등록부의 credential/profile 참조도 웹 응답에서 숨긴다. HTTP는 기존 인증·동일 출처·한도·오류 처리를 유지한다.

## 최신 조사에서 보존할 사실

- 실제 TikTok 설정은 `tiktok_web.daily=true`, direct `tiktok.enabled=false`다. 자동 작업 메모의 daily=false는 낡은 근거다. 현재 설치 TikTok 큐 plist는 없으며 load/disabled는 미확인이다. enqueue 허용과 큐 가동을 같은 활성 상태로 합치지 않는다.
- 숏츠 전용 TikTok 경로와 범용 YouTube 업로드 경로의 공개/쿠팡 제외 조건이 다르다. GeoAI Threads도 저녁 조건 외 명시 `--threads` override가 있다.
- 설치 plist 기준 채용은 일21:00, 진로는 화20:00, 재난 교차는 화·금19:30이며 주석·백업과의 차이를 보존한다. 기존 작업을 새 스케줄로 옮기지 않는다.
- 현재 DB v1의 events는 콘텐츠 전용이다. 배포 이력은 새 테이블로 두고 미디어·원문 파일은 변경하지 않는다.

## 공통 계약

### 등록부와 미리보기 컨텍스트

신규 `models.py`는 frozen dataclass/tuple 기반의 `Registry`, `Connection`, `ExecutionRequest`, `ExecutionContext`와 `ContractError(code)`를 제공한다. 기존 전체 계획 T2의 의미를 유지하되 이 단계 컨텍스트는 항상 dry다.

- `load_registry(path:Path)->Registry`: schema_version/revision, accounts, connections, jobs, policies, crossposts를 읽고 중복·미존재 참조·소유 불일치를 검증한다. 단순 조회가 파일을 만들지 않는다.
- `resolve_context(request,registry,content_owner_account_id,*,allow_unverified=False)->ExecutionContext`: 요청은 job_id/connection_id/content_id/revision/publication_purpose/schedule_slot만 지정한다. destination/target/policy/credential/profile/execution_owner는 서버 등록부에서만 확정한다. 미확인 대상 초안 저장에서만 서버가 allow_unverified=True를 넘기며 승인·준비에서는 False다.
- `validate_observed_target(ctx,observed:dict)->None`: fixture observed의 platform/target_id/authenticated/login_subject/verification_method를 검증한다. 실제 플랫폼은 조회하지 않는다.
- 실제 target ID가 미확인인 연결은 UI에서 선택·계획 저장은 가능하되 `target_status=unverified`와 차단 이유를 보존한다. 승인 subject를 고정하거나 가짜 prepare를 통과시키지는 않는다.

공용 `normalize_schedule(value:str,timezone:str='Asia/Seoul')->str`은 aware ISO만 받아 UTC ISO로 반환한다. IANA zone과 offset이 불일치하거나 DST 모호/존재하지 않는 시각은400이다. naive 입력은 받지 않는다.

새 로컬 계획용 작업 ID는 `managed.personal.plan`, `managed.dept.plan`이며 콘텐츠 소유 계정으로 서버가 선택한다. schedule_owner=console, execution_owner=managed, planning_enabled=true, enabled=false로 등록한다. planning_enabled만 계획 저장을 허용하며 실행은 비활성이다. legacy 작업은 원장 미리보기에서 관측만 하고 이 두 새 계획용 작업으로 바꾸지 않는다.

### 불변 배포·승인

배포 초안은 특정 content_id/revision/manifest_hash와 변환본 키(destination_account_id,platform)를 참조한다. ContentStore 변환본의 형식은 바꾸지 않는다. 서버가 owner/destination/connection/target/registry_revision/policy_revision을 확정하고 고정 JSON context를 저장한다.

- `approval_fingerprint(snapshot:dict,context:dict)->str`: 원문·선택 변환본·출처·순서 있는 자산 해시·필수 검토 근거·owner/destination/target·공개 옵션·publication_purpose·허용 일정 조건·정책/등록부 revision을 정규 JSON SHA256으로 묶는다. 검토 시각과 JSON 객체 키 순서는 영향을 주지 않는다.
- `is_approval_current(record,snapshot,context)->bool`: decision=approved, 정확한 해시·버전·정책 일치를 요구한다. 수동 reviews를 발행 승인으로 취급하지 않는다. 현재 로그인 성공과도 별개다.
- 승인 decision은 approved/rejected/revoked, source는 manual이다. actor는 서버가 `console_user`로 기록한다. 자동 승인은 이 단계에 도입하지 않는다.
- 이 단계 승인의 scope는 plan이다. 해시에 scope와 dry 모드를 포함하며 후속 실제 발행 승인으로 재사용하지 않는다. 독립 검산·출처 검토가 필요한 실제 발행 승인은 후속 실행 관문에서 별도 증거·정책으로 재확인한다. UI는 ‘계획 승인’으로 명시한다.
- 배포 상태는 pending/ready/cancelled만 변경할 수 있다. ready는 ‘계획 승인됨 · 실행 안 함’이다. submitting/uploaded/scheduled/published/verified/unknown은 API에서 설정할 수 없다.

### 원장·일정

`Ledger(root:Path)` 생성·읽기는 무쓰기이며 `initialize()`만 스키마를 초기화/이행한다.

- `create_or_get_run(request:dict)->dict`: UNIQUE(job_id,scheduled_at_utc,phase). phase=prepare/verify, mode=dry 고정. 같은 키·다른 불변 요청 hash는409다.
- `create_or_get_delivery(request:dict)->dict`: UNIQUE(content_id,revision,connection_id,publication_purpose,schedule_slot). 같은 키/본문은 동일 ID, 다른 context는409다. 재시도·시간 이동으로 새 ID를 만들지 않는다.
- `get_delivery(id)->dict|None`, `list_deliveries(account='all',content_id=None)->list`, `events(id)->list`.
- `record_approval(delivery_id,expected_version,subject_hash,decision,notes)->dict`: 서버 재계산 hash·불변 원고·등록부/정책과 CAS를 같은 짧은 트랜잭션에서 확인하고 승인/배포/이력을 원자적으로 저장한다.
- `preview_schedule(delivery_id,expected_version,proposed_time,timezone)->dict`: 저장0. 예상 version/context/시각/정책의 preview_hash, 승인 유지 여부, 영향받는 교차 경로, 이유를 반환한다.
- `reschedule(delivery_id,expected_version,proposed_time,timezone,preview_hash)->dict`: preview를 서버 재계산해 확인하고 동일 ID/slot의 시각을 바꾼다. 일정 조건 범위 밖이면 pending으로 되돌리고 승인 이력을 보존한다.
- `cancel(delivery_id,expected_version)->dict`: 미실행 로컬 계획만 cancelled로 전환한다. 원격 예약 취소를 뜻하지 않는다.

모든 공개 응답은 source=managed, schedule_kind=local_plan, remote_state=unavailable, execution_enabled=false를 포함한다. 자격증명 참조·프로필·원본 저장 경로·내부 context의 비밀 필드는 제거한다.

배포 응답의 공통 필드는 `id,content_id,revision,manifest_hash,owner_account_id,destination_account_id,connection_id,platform,target_label,target_status,publication_purpose,schedule_slot,scheduled_at,timezone,schedule_condition,status,version,subject_hash,approval,blockers,source,schedule_kind,remote_state,execution_enabled,created_at,updated_at`다. approval은 null 또는 `{id,scope,decision,subject_hash,content_revision,source,recorded_at}`다. blockers는 코드·표시 이유 객체 배열이다. `/connections`의 items는 `{id,account_id,platform,target_label,target_status,capabilities,planning_enabled,auth_status,execution_enabled:false}`만 제공한다. `/events`는 `{items:[{id,version,kind,summary,created_at}]}`다.

run request는 job_id/scheduled_at_utc/phase/source/request_kind이며 source=console, request_kind=manual_plan으로 서버가 고정한다. phase=prepare를 생성하고 verify는 가짜 어댑터 시험에서만 별도 유일키를 검증한다. 배포 create 요청의 run과 context는 서버가 생성하므로 클라이언트 run_id/context 입력은 받지 않는다.

일정 조건은 `{kind:'fixed',at:awareISO}` 또는 `{kind:'window',from:awareISO,to:awareISO}`다. 생성 시 실제 시각이 fixed와 같거나 window의 from 이상/to 미만이어야 한다. 범위 안 이동은 조건을 유지한다. 범위 밖 이동의 preview는 새 fixed 조건과 승인 무효화를 함께 보여주며 저장 시 그 새 조건을 확정한다. 승인 이력의 옛 조건은 수정하지 않는다. preview_hash에는 현재 배포 version/현재 조건/새 조건/시각/등록부·정책 revision을 포함한다.

## 검토 중점

1. 기존 v1 데이터·자산을 보존하고 이행 실패/미래 버전에서 반쪽 DB를 만들지 않음 → S3.
2. 같은 회차·배포의 두 창 요청은 중복 저장하지 않고 다른 본문은409 → S3/S4.
3. 원문·대상·정책·게시 자산 순서·허용 범위 밖 시각 변경은 과거 승인을 재사용하지 않음 → S2/S3.
4. 기존 조건·중지/미확인/서로 다른 근거를 단순 활성값으로 합치거나 지연을 두 번 더하지 않음 → S2.
5. 개인 원본·학과 배포의 소유권과 조회 범위를 유지하고 선호 설정으로 권한을 만들지 않음 → S1/S3/S4.

## S3. v2 원장·승인·일정 API

**소유:** `common/operations/{database,ledger}.py`, `ax-console/app/{web_deliveries,workspace_snapshot,web_server}.py`, `tests/test_operations_ledger.py`, `tests/test_web_deliveries.py`. HTTP 공용 파일은 이 담당만 수정한다.

- [ ] v1→v2 보존/rollback/미래 버전 거부/읽기 무이행, 같은 회차·배포 CAS경쟁, 승인/이력 rollback, 오래된 일정 preview409를 RED로 확인한다.
- [ ] initialize_database의 명시적 이행에만 v2 jobs/triggers/runs/approvals/deliveries/delivery_events를 추가한다. v1 기존 테이블과파일은 유지한다. 기존 초기화·연결 버전 검사를 함께 갱신한다. v1 자동 GET 이행은 없고 v2 기능은503이다. attempts/permit/quota/lease 테이블만 만들어 구현됐다고 표시하지 않는다.
- [ ] Ledger 메서드와 인증 HTTP를 구현한다. GET `/api/v2/connections`, `/api/v2/deliveries?account=&content_id=`, `/api/v2/deliveries/<id>`, `/<id>/events`; POST `/api/v2/deliveries/preview`(순수), `/api/v2/deliveries`(계획), `/<id>/approvals`, `/<id>/schedule-preview`, `/<id>/cancel`; PUT `/<id>/schedule`. 목록은 `{items:[]}`, 단일/쓰기 성공은 전체 배포 객체다. JSON한도1MiB·기존 오류400/401/404/405/409/413/503을 적용한다.
- [ ] preview/create body는 content_id/revision/manifest_hash/connection_id/publication_purpose/schedule_slot/scheduled_at/timezone/schedule_condition/options/crosspost_rule_id다. 최초 client_version은 없고 수정은 expected_version 필수다. publication_purpose는 initial/followup/republication, schedule_slot은 `[a-zA-Z0-9][a-zA-Z0-9_.:-]{0,99}`이며 생성 후 고정한다. options 허용값은 visibility(public/unlisted/private), title_override(300자), description_override(200000자)만이며 서버 registry capabilities와 대조한다. actor/owner/destination/target/status/execution_enabled override는400이다.
- [ ] 관리 snapshot에 로컬 계획/승인 상태를 합치고 legacy 원격 예약과 구분한다. 승인해도 실행·예약 타이머를 시작하지 않는다. 시간 이동은 새로운 배포를 만들지 않는다.
- [ ] Python·기존 회귀 GREEN, 원본 파일 불변·실제 발행/프로필/타이머0을 확인하고 부모가 커밋한다.

## S4. 배포 계획·승인·캘린더 화면

**소유:** `ax-console/app/web/delivery_editor.js`, `content_editor.js`, `app.js`, `api.js`, `view_helpers.js`, `styles.css`, `tests/test_delivery_editor.mjs`. 새 정적 모듈 allowlist는 S3 담당에게 전달한다.

- [ ] 순수 폼/상태 시험으로 실제 대상 미확인·local_plan 라벨·승인 hash/CAS·시간 영향 미리보기·늦은 계정 응답/409 초안 보존을 RED로 고정한다.
- [ ] 관리 원본 상세에 배포 계획·승인 버전·대상/차단 이유·이력을 연결한다. 승인과 수동 검토, 선호와 실제 등록 연결을 구분한다. target 미확인은 저장 가능하지만 승인/준비 버튼은 비활성이다.
- [ ] 캘린더는 로컬 계획/legacy 원격 예약 기록을 구분한다. 시간 변경은 영향 미리보기→변경 저장 순서이며 승인 유지/재검토·교차 지연·원격 변경 없음이 보인다. 교차 화면은 실제 기존 규칙과 미리보기를 표시하며 legacy 수정은 비활성이다.
- [ ] Node GREEN 및 임시 브라우저에서 생성→승인→범위 안/밖 일정 변경→취소, 개인 원본/학과 대상, 두 창 충돌,320/1280px·키보드·빈/실패 상태를 확인하고 커밋한다. 플랫폼 예약·게시 성공 숫자를 만들지 않는다.

## 통합 수락과 후속 범위

- [ ] 공통 메서드·필드·스키마/정적 모듈을 작업 전 대조하고 부모가 공유 인덱스 커밋을 직렬 수행한다. 각 작업 독립 검토와 전체 단계 검토를 수행한다.
- [ ] v1 임시 자료 이행 및 HTTP·화면 수락 증거, 기존 모든 Python/Node 회귀, source_root 파일 불변과 실제 외부 실행0을 기록한다.
- [ ] 실제8769 관리 DB 이행은 검증·백업 뒤 별도 적용한다. 기존8700·운영 source_root·launchd·교차 실행 주인은 유지한다.

이 단계는 전체 T5/T6/T9 또는 자동 발행 시스템 완료가 아니다. 실제 대상 인증·제작 실행 분리·STOP/잠금/한도/permit/lease·불확실 응답 복구·플랫폼 제출/공개검증·성과·보호된 외부 접속·운영 이행은 후속 단계에서 완성한다.

## 자체 점검

확정 화면의 3단계 경계에 따라 실제 제출을 제외했다. S1이 생산하는 컨텍스트/시간 계약, S2의 승인·교차 계산, S3의 원장/HTTP, S4의 응답 필드를 대조했다. 검토 중점5개를 각 작업의 실패 시험에 배정했다. 선호·인증·계획 승인·실제 발행 승인을 합치지 않는다. 확인되지 않은 실제 대상과 현재 설정/주석의 충돌은 삭제하지 않는다. 이 문서는 향후 구현 계획이며 작업·시험 완료 기록이 아니다.

## S5. 화면 수락에서 확인한 교차 규칙 조회 연결

S4의 ‘실제 기존 규칙 표시’가 초기 자동 작업 관측값에만 연결돼 등록부의23개 규칙이 교차 화면에 나오지 않는 것을 수락 시험에서 확인했다. 실행 기능을 추가하지 않고 조회 연결만 보완한다.

**소유:** 신규 `common/operations/crosspost_catalog.py`, `ax-console/app/workspace_snapshot.py`, `web/app.js`, 필요 시 `view_helpers.js`, `tests/test_crosspost_catalog.py`, 조회 조합 시험 추가.

- [ ] Registry의 owner 또는 destination 관련 계정으로 필터한 안전한 요약, 기존 관측값 보존·별도 개수, 비밀/절대 경로 미노출·조회 무쓰기를 시험한다.
- [ ] snapshot.crossposts에는 등록된 요약, legacy_crosspost_observations에는 기존 관측을 분리하고 crosspost_catalog_status로 미수집을 표시한다. 등록부를 읽지 못하면 기존 관측을 없애지 않는다. 새 규칙을 자동 실행하지 않는다.
- [ ] 교차 화면에서 등록 규칙·자동 작업 관측·배포 계획/기록을 구분하고 조건·활성 근거·기존 실행 주인을 한국어로 표시한다. 기존8메뉴·읽기 전용 fallback을 유지한다. 집중 시험·독립 검토·실제 UI 조회를 확인한다.
