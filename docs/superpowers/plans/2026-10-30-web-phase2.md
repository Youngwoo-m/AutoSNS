# 계정별 콘텐츠 저장·연동 설정 2단계 구현 계획

> 구현은 `superpowers:subagent-driven-development`를 적용한다. 독립 파일 소유권을 나누고 통합·커밋은 부모가 수행한다.

**Goal:** 확정된 기획·보관함 화면에서 개인/학과 원본·버전·변환본·자산·검토를 저장하고, 계정별 SNS 도구 선택을 관리한다.
**Architecture:** 기존 자료는 읽기 전용으로 유지한다. 새 관리 자료는 별도 로컬 저장 루트의 SQLite 및 불변 파일에 저장하고 기존 조회 화면에서 출처를 구분해 함께 조회한다. 발행·제작 실행 연결은 이후 단계다.
**Tech Stack:** Python 표준 라이브러리 SQLite·파일 해시, 기존 독립 웹 인증, buildless JavaScript.
**Spec:** [확정 화면 및 추가 SNS 범위](../specs/2026-10-30-account-web-screens-design.md), [승인 운영 설계](../specs/2026-10-30-account-channel-automation-design.md).

## 공통 제약

- `AX_WORKSPACE_ROOT`는 서버 시작 때 명시한 새 저장 루트다. 기본값으로 운영 루트를 쓰지 않는다. 미설정이면 기존 조회 전용으로 실행한다.
- 기존 server.py의 content_approve/content_draft/csave를 호출하지 않는다. 저장·검토는 예약이나 자동 작업을 생성하지 않는다. 기존 JSON·토큰·프로필·launchd·STOP은 변경하지 않는다.
- 개인·학과만 원본 소유자가 될 수 있다. 원본 소유권은 생성 후 고정한다. UI 조회 필터는 저장 소유권의 암묵적 기본값이 아니다.
- 목표 채널은 기획 메타데이터다. 연결 성공·발행 권한·예약을 뜻하지 않는다. 개인 원본과 학과 대상 계획을 함께 보존한다.
- 새 저장소는 `operations.sqlite3`, 계정별 파일은 `<account>/content/<id>/revisions/<revision>/`에 둔다. 원문·미디어 바이트는 파일로, 상태·해시·참조는 DB로 관리한다. 기존 JSON과 양방향 동기화하지 않는다.
- 비밀번호·토큰 입력/저장·외부 서비스 호출은 이 단계에 넣지 않는다. 플러그인 설치나 서비스 연결을 가장하지 않는다. 설정 활성은 웹의 사용 선호만 나타내며 기존 자동 작업을 바꾸지 않는다.
- API 쓰기는 기존 로그인·같은 출처 검사에 추가해 정확한 JSON 스키마와 요청 크기를 검증한다. 사용자 제공 디스크 경로를 받지 않는다.

## 검토 중점

1. 두 창의 동시 저장은 마지막 요청으로 덮어쓰지 않고 409 충돌로 표시 → P1/P3.
2. 파일 저장 실패·프로세스 중단 시 현재 버전이 반쪽 파일을 참조하지 않음 → P1.
3. 구자료 ID와 새 관리 ID가 겹쳐도 잘못 편집하거나 소유 계정을 바꾸지 않음 → P2/P3.
4. 자산 이름의 경로 우회·실행 파일·한도 초과가 서버 경로나 비밀을 읽거나 실행하지 못함 → P1/P2.
5. 원문·변환·자산 수정 후 이전 버전의 검토 결과를 현재 검토 완료로 사용하지 않음 → P1/P3.

## 공통 계약

신규 `common/operations/content_store.py`의 `ContentStore(root:Path)`는 명시적 `initialize()` 뒤에만 쓴다. 읽기 메서드는 디렉터리·DB를 만들지 않는다. `StoreError(code)` 및 `ConflictError`를 정의한다.

- `create(owner_account_id:str, payload:dict)->dict`
- `update(content_id:str, expected_revision:int, payload:dict)->dict`
- `get(content_id:str)->dict|None`, `list(account:str='all')->list[dict]`
- `add_asset(content_id:str, expected_revision:int, filename:str, media_type:str, data:bytes)->dict`: 새 revision 생성.
- `record_review(content_id:str, revision:int, manifest_hash:str, kind:str, decision:str, notes:str)->dict`: 해당 불변 버전에만 귀속. 실제 독립 검토 실행 여부는 별도 표시.

content 응답: `id(managed_ 접두사), source=managed, owner_account_id, revision:int, title, kind(article/card/short/video), series, status(idea/drafting/review/archived), original, variants:[{destination_account_id,platform,text}], sources:[{url,note}], assets:[{id,filename,media_type,size,sha256}], manifest_hash, reviews, created_at,updated_at`. ID·파일 경로는 서버가 생성한다. 데이터에 경로·credential_ref를 넣지 않는다. 2단계에서는 승인 상태를 만들지 않는다.

JSON payload 한도 1MiB, title 300자, original/각 변환본 200000자, sources 최대100·변환본 최대30. 자산은 JPEG/PNG/WebP·MP4·MP3/WAV 허용, 파일당100MiB·콘텐츠 합계500MiB. 확장자·시그니처·타입 조합을 확인하며 SVG/HTML·실행 파일은 받지 않는다. 크기 초과는413, 스키마 오류400, 없는ID404, revision충돌409, 저장실패503.

## 계획 자체 점검

화면 2단계의 원본·버전·자산·검토·채널 변환 저장은 P1~P3에, 추가 SNS의 계정별 사용 설정은 P4에 배정했다. 외부 로그인·비밀 보관·실행 연결은 별도 후속 범위로 남겼다. 공통 ContentStore 계약과 HTTP 오류·한도를 맞췄으며 검토 중점 5개를 각 소유 시험에 연결했다. 기존 운영 설계의 승인·실행·배포 상태는 콘텐츠 편집 상태와 합치지 않는다. 이 문서는 향후 구현 계획이며 시험 통과 기록이 아니다.

## 착수 전 계약 보완 (독립 검토 반영·이 절이 우선)

사용자가 2단계 개발 시작을 승인했다. 아래는 기존 범위 안에서 구현자가 공유할 세부 계약을 고정한 것이다.

- P1이 `common/operations/database.py`도 소유한다. `initialize_database(root:Path)->None`, `connect_database(root:Path, *, writable:bool=False)->sqlite3.Connection`를 제공한다. 미존재 DB의 읽기 연결은 파일을 만들지 않고 `FileNotFoundError`다. 모든 연결에 foreign_keys=ON·busy_timeout=5000, 쓰기 rollback journal=DELETE, connection context 뒤 명시적 close를 적용한다. 스키마 v1은 한 트랜잭션으로 콘텐츠와 연동 설정 테이블을 모두 초기화한다. 초기화 순서/동시 실행 시험은 P1 소유다. schema version이 다르면 쓰지 않는다.
- 공통 연동 테이블 `integration_settings(account_id TEXT, provider_id TEXT, connection_id TEXT, revision INTEGER, payload TEXT, created_at TEXT, updated_at TEXT, PRIMARY KEY(account_id,provider_id,connection_id))`, `integration_events(id INTEGER PRIMARY KEY, account_id TEXT, provider_id TEXT, connection_id TEXT, revision INTEGER, created_at TEXT)`도 P1 DDL 소유다. P4는 이 테이블만 사용하며 독립 DDL·user_version 변경을 하지 않는다.
- `get(content_id, revision:int|None=None)`와 `list_revisions(content_id)->list[{revision,manifest_hash,created_at}]`를 추가한다. `read_asset(content_id,revision,asset_id)->tuple[dict,bytes]`는 DB에 귀속된 파일만 읽고 hash·size를 검증한다. 미존재 ID/버전/자산은 StoreError('not_found')다.
- create/PUT 편집 필드는 `title,kind,series,status,original,variants,sources`다. title/kind는 필수, 나머지 기본값은 `'',idea,'',[],[]` 순이다. PUT은 이 편집 필드 전체 교체이며 기존 자산은 유지한다. 소유 계정은 create의 독립 인자로만 받고 서버 전용 필드는 거부한다. HTTP create만 owner_account_id, PUT만 expected_revision을 추가로 받는다. 상태에는 `production`도 포함한다. 검토를 해도 status를 자동 승인으로 바꾸지 않는다.
- variants의 목적 계정은 dept/personal, platform은 youtube/tiktok/instagram/threads/x/facebook/tistory/naver_blog/blogger/homepage/kakao만 허용한다. 동일 (destination_account_id,platform) 중복은 거부한다. HTTP create/PUT 성공 응답은 전체 content 객체이며 GET 상세도 동일하다.
- 파일은 요청별 UUID 경로에 먼저 준비한다. `BEGIN IMMEDIATE`에서 예상 현재 revision을 확인하고 덮어쓰지 않는 불변 최종 경로로 이동한 뒤 revision 삽입·포인터 CAS·commit 한다. 최종 파일 경로에 요청 UUID를 포함해 rollback 잔여 파일 때문에 같은 revision 재시도가 막히지 않게 한다. 정리는 자신이 만든 미참조 경로만 수행하며 외부·승자 파일을 삭제하지 않는다. 동시 저장·이동 후 commit 실패 시험을 추가한다.
- manifest_hash는 owner/title/kind/series/status/original/variants/sources/assets의 정규 JSON(sort_keys, ensure_ascii=False, separators=(',',':')) SHA256이다. 자산은 id/filename/media_type/size/sha256 순서 있는 목록이고 시각·검토는 제외한다. 검토 kind=calculation/source/general, decision=pass/changes_requested, method=manual. 검토 레코드 id/revision/manifest_hash/kind/decision/notes/method/created_at을 반환하며 해당 revision/hash의 일치가 필수다. notes 최대10000자, sources note 최대2000자·url은 절대 http/https만이다.
- 500MiB는 콘텐츠에 귀속된 고유 자산 바이트 합계이며 과거 버전 재사용은 중복 계산하지 않는다. 사용자 filename은 표시용 최대200자로 /·\\·NUL·CR·LF를 거부하며 실제 저장 이름은 서버 생성 ID다. 문자열 한도는 문자 수, HTTP JSON 한도는 UTF8 바이트다.
- 자산 업로드는 `Content-Type`, `Content-Length`, percent-encoded UTF8 `X-AX-Filename`, 십진수 `X-AX-Expected-Revision` 헤더와 raw body를 사용한다. 길이 누락400·초과413·짧은body400, 허용되지 않는 타입415. 성공은 새 전체 content 반환이다. 기존 자산 ID는 후속 버전에도 유지한다. GET `/api/v2/contents/<id>/revisions/<revision>/assets/<asset_id>`는 인증 후 전체200만 제공하고 Range는416으로 명시적으로 거부한다. Content-Disposition filename은 RFC5987로 인코딩한다. 자산 JSON에는 이 경로의 `url`을 API에서 덧붙인다.
- GET `/api/v2/contents/<id>/revisions`와 GET `/api/v2/contents/<id>?revision=N`을 추가한다. 과거 버전은 읽기 전용이다. 모든 편집·자산 쓰기·선호 설정 수정은 현재 revision CAS가 필요하다.
- P2 소유에 `ax-console/app/workspace_snapshot.py`를 추가한다. `build_workspace_snapshot(source_root,workspace_root,account='all',**kwargs)`는 legacy 조회 결과에 `source=legacy`, 새 콘텐츠에 `source=managed`를 부여해 합친다. 신규 요약은 기존 필드와 `target_accounts`를 포함하고 summary는 original의 앞300자, channels는 목표 platform 고유 목록이다. 소유 또는 목표 계정에 관련되면 포함하며 계획만으로 deliveries/schedule을 생성하지 않는다. `read_only=true`는 운영 자료 조회 성질을 유지하며 `workspace_writable:boolean`을 별도 제공해 편집 지원을 알린다. P3가 view_helpers.js도 소유하고 관련 계정 필터에서 target_accounts를 보존한다. 기존 미설정 읽기 화면은 그대로 동작한다.
- P4 계약: `IntegrationStore(root).initialize()`, `.list(account='all')->list[dict]`, `.put(account_id,provider_id,connection_id,expected_revision,payload)->dict`. 첫 저장 expected_revision=0, 이후 일치 필수. payload는 platform/target_label/enabled_preference/notes이며 target_label최대300, notes최대2000, enabled_preference는 bool 필수다. connection_id는 `[a-z0-9][a-z0-9_-]{0,63}`. 응답은 키3개와 revision,payload필드,created_at,updated_at,connection_status=unknown,execution_status=not_connected. 토큰·추가필드는 거부한다.
- P4 플랫폼 allowlist: metricool=instagram/threads/x/facebook/youtube/tiktok, vidiq=youtube/instagram/tiktok, local=youtube/tiktok/instagram/threads/x/facebook/tistory/naver_blog/blogger/homepage/kakao. 이는 설정 후보 allowlist이며 구현·연결 성공을 증명하지 않는다. GET `/api/v2/integrations/settings?account=all|dept|personal`는 `{items:[...]}`, PUT 동일 경로 body는 account_id/provider_id/connection_id/expected_revision 및 payload 필드만이다. P4는 저장소·검증 도우미 및 독립 UI 모듈, P2/P3는 공용 라우팅·화면 조합을 담당한다.
