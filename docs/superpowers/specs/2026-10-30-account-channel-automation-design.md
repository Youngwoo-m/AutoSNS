# 개인·학과 계정별 채널 자동 운영 설계

- 작성일: 2026-10-30, Asia/Seoul
- 상태: 상세 설계 작성·독립 검토·사용자 승인 완료. 단계별 실행 계획 작성 완료이며 운영 적용 없음.
- 선행 근거: [현황 점검](../../audits/2026-10-30-account-automation.md)
- 사용자 결정: 현재 교차 게시 방식 유지. A(실행 규칙 통일 후 폴더 분리) 선택.
- 설계자가 제안한 기술 선택: 기존 Python·AX 콘솔·axlock 재사용, SQLite 실행 원장, 계정 컨텍스트 명시, 채널별 배포 작업. 사용자가 세부 기술을 지정한 것으로 표현하지 않는다.

## 1. 목적과 범위

개인·학과 계정을 각각 운영하면서 공용 제작·검토 기능과 운영 콘솔을 공유한다. 각 콘텐츠의 기획·작성·검토·제작·예약·발행·공개 검증·성과를 한 흐름으로 추적한다. 원본 소유 계정과 실제 게시 대상 계정은 별도로 기록한다.

이번 산출물은 현황·설계·단계별 실행 계획이다. 운영 코드 구현, 인증 갱신, 공개 게시, 스케줄 변경, 꺼진 작업 활성화, 원격 배포는 별도 구현 단계의 일이다. 이 설계 승인도 실제 게시나 기존 자동화의 활성화 승인을 대신하지 않는다.

### 최종 목표

- 계정·채널·대상을 게시 전에 검증하고 잘못된 자격증명이나 기본값을 차단한다.
- 계정별 일정·승인·한도·예산·콘텐츠·실행 이력을 구분한다.
- 기존 교차 게시의 대상·콘텐츠 변환·시점·간격·중복 방지 조건을 보존한다.
- 중단·응답 유실·부분 실패를 기록하고 중복 게시 없이 재개할 수 있게 한다.
- 공개 검증된 게시물의 성과를 다음 기획에 연결한다.
- 사람은 정책, 로그인 재인증, 결과가 불확실한 게시와 검토 예외를 처리한다.

### 하지 않을 것

- 프로젝트를 학과·개인 두 서비스로 재작성하거나 모든 채널에 새 외부 SaaS를 강제하지 않는다.
- 현재 운영하지 않는 개인 Instagram·TikTok 등을 존재한다고 가정하지 않는다.
- 비활성 작업을 폴더 정리나 등록부 통일 과정에서 켜지 않는다.
- 플랫폼이 보장하지 않는 원격 게시의 exactly-once를 보장한다고 주장하지 않는다.

## 2. 접근 비교와 선택

| 접근 | 장점 | 대가 | 결정 |
|---|---|---|---|
| A. 실행 규칙을 통일한 뒤 폴더 분리 | 기존 발행기를 활용하고 계정 경계를 먼저 검증 | 전환 동안 구경로·신규 계약 공존 | 사용자 선택 |
| B. 폴더·데이터 이동부터 진행 | 소유권을 먼저 시각적으로 정리 | import·설정·가상환경·스케줄 동시 변경 | 첫 단계로 채택하지 않음 |
| C. 계정별 별도 프로젝트·서비스 | 배포·장애 격리 강화 | 공용 기능 중복·운영 부담 | 채택하지 않음 |

A에서는 실행 계약·관측·복구를 먼저 붙이고 동일 동작이 확인된 모듈만 이동한다. 현재 운영 경로와 이전 전 자료가 서로 다를 수 있으므로 최신 작업 정의·비활성 설정·실행 파일을 이행 기준으로 캡처한다.

## 3. 전체 구조와 책임

```text
계정 정책·작업 등록부
       ↓
launchd / 콘솔 / 명시적 수동 요청
       ↓ 실행 요청 수집(중복 키)
실행 원장(SQLite) ← 운영 콘솔·사건·성과 조회
       ↓
실행 워커 → 기획·초안·검토·제작
       ↓ 승인된 콘텐츠 버전
대상별 배포 작업 → axlock·한도 예약·대상 확인 → 채널 어댑터
       ↓
업로드/예약/공개 상태 조회 → 공개 검증 → 성과 → 다음 기획
```

- `common/`: 계정을 묵시적으로 선택하지 않는 기반. 잠금·실행·상태·검증·채널 어댑터·미디어·검토 계약.
- `dept/`, `personal/`: 계정별 정책·작업 정의·원본 콘텐츠·산출물·이력의 소유자.
- `ax-console/`: 통합 화면, 입력 검증, 정책 편집, 스케줄·사건·성과 조회. 화면의 계정 선택만으로 인증을 추정하지 않는다.
- 기존 발행기: 전환 초기에 실제 채널 동작을 담당하는 호환 실행기. 임의 셸 명령을 받지 않고 등록된 실행기 ID만 호출한다.
- 플러그인: 선택적 조사·제작·분석 공급자. 대화에서 설치된 Metricool·vidIQ를 무인 작업의 실행 의존성으로 간주하지 않는다.

## 4. 등록부와 실행 컨텍스트

등록부는 비밀값 대신 참조만 가진다. 논리 모델은 다음과 같으며 파일·테이블 상세 형식은 구현 계획에서 정한다.

| 항목 | 필수 내용 |
|---|---|
| 계정 | `account_id`(dept/personal), 표시명, 정책·예산 참조 |
| 채널 연결 | `connection_id`, `account_id`, 플랫폼, 불변 대상 ID, 표시 주소, 자격증명·프로필 참조 |
| 기능 상태 | 작성·초안·업로드·예약·공개조회·성과조회 각각 지원 여부, 인증 확인 시각 |
| 작업 | `job_id`, 소유 계정, 실행기 ID, 스케줄 원천, 시간대, 활성 상태, 허용 대상 연결, 잠금·한도 참조 |
| 교차 게시 | 규칙 ID, 원본 소유 계정, 대상 연결, 트리거, 변환, 지연·간격, 중복 키 규칙 |
| 정책 | 승인 조건, 주제·채널별 한도, 예산, 재시도 상한, 예외 처리 |

`common`은 유지보수·보고 등 내부 작업 소유 유형이며 공개 발행 계정으로 허용하지 않는다. 구현·인증 확인·사용자 활성화·최근 성공 상태는 각각 별도 필드로 표현한다.

채널 연결은 예를 들어 `personal.naver.safeworking`, `dept.youtube.main`처럼 안정적인 논리 ID로 구분하되, 실제 플랫폼 ID를 표시명에서 유추하지 않는다. 동일 플랫폼의 여러 채널을 수용한다. 홈페이지·Kakao 알림은 보조 채널 유형으로 구별한다.

호출자는 등록된 `connection_id`와 작업 의도만 선택한다. 자격증명·프로필·대상 ID·잠금·한도는 등록부에서 해석하며 외부 입력이 임의로 덮어쓸 수 없다. 기존 환경변수는 검증된 값만 자식 프로세스별로 전달한다.

모든 실행은 `run_id`, `job_id`, `owner_account_id`, `content_id/revision`, `connection_id`, `destination_account_id`, `target_id`, `credential_ref`, `profile_ref`, `policy_revision`, `schedule_slot`, `dry_run`을 명시한다. 제작 단계처럼 대상이 없는 작업은 대상 필드를 비워 둔 별도 작업 유형이며 공개 발행 함수를 호출할 수 없다.

### 게시 전 불변 조건

1. 알려진 작업·계정·연결만 허용한다. `dept`가 아닌 값을 개인으로 처리하는 분기는 제거한다.
2. 콘텐츠 소유 계정과 요청 소유 계정이 일치해야 한다. 교차 게시 시에도 소유권은 유지하고 대상 계정만 규칙에 따라 바꾼다.
3. 대상 연결의 계정·플랫폼·불변 ID와 인증 계정에서 조회한 실제 대상이 일치해야 한다. OAuth 이메일만으로 채널 일치를 판정하지 않는다.
4. 실제 대상을 확인할 수 없으면 게시하지 않고 `needs_auth` 또는 `needs_review`로 보낸다. 브라우저 채널은 로그인 사용자와 글쓰기 대상 블로그·채널을 확인한다.
5. 자격증명은 연결에 등록된 참조만 해석한다. 누락 시 다른 계정 토큰·프로필·설정으로 넘어가지 않는다.
6. 알림·자막·댓글·메타데이터 수정 등 후처리도 동일 대상 연결을 사용한다. 신규 댓글·외부 전송 권한을 설계만으로 확대하지 않는다.

기존 암호화 비밀 저장소·키 이름·실제 로그인 디렉터리는 초기 단계에서 그대로 유지한다. 토큰 이름과 파일 경로의 호환은 명시적 매핑으로 감싸고, 콘텐츠나 실행 로그에 토큰·쿠키를 복사하지 않는다.

## 5. 현재 채널의 이행 범위

| 계정 | 연결 대상 | 초기 연결 방식 | 최종 운영 범위 |
|---|---|---|---|
| 학과 | 네이버·Blogger·X | 기존 콘솔 어댑터를 새 계약으로 감쌈 | 초안/게시/결과 검증/성과 중 실제 지원 기능 |
| 학과 | YouTube·Instagram·Threads·TikTok | 기존 스크립트·대기열 호환 | 제작·예약 또는 즉시 게시·공개 검증 |
| 개인 | Blogger | 기존 콘솔·GeoAI 발행기 호환 | 동일한 실행·결과 계약 |
| 개인 | Tistory·YouTube | 기존 Claude·전용 발행기 호환 | 생성 결과와 게시·예약·후처리 분리 추적 |
| 개인 | 네이버 safeworking | 전용 발행기를 등록부·기획·중복 조회에 연결 | 기존 Tistory 교차 게시 보존 |
| 개인 | 홈페이지·Kakao | 보조 실행기로 분류 | 요청 접수·알림과 SNS 공개 게시 구별 |

기능 지원과 로그인 상태는 별개다. 현재 미연결인 채널은 목록에서 준비 상태를 표시하되 스케줄을 활성화하지 않는다. 어떤 계정이든 실제 구현에 예약·성과 API가 없으면 미지원으로 표시하고 날짜 필드만으로 지원한다고 주장하지 않는다.

## 6. 콘텐츠·실행·배포 상태

콘텐츠는 원본과 채널별 변환본, 제작 자산, 검토 결과를 버전으로 고정한다. 승인된 버전과 정책 버전의 해시를 저장하며, 승인 뒤 본문·이미지·대상·공개 시점을 변경하면 영향을 받는 대상의 승인을 다시 확인한다.

| 단위 | 상태 예시 | 의미 |
|---|---|---|
| 콘텐츠 | idea → drafting → review → approved → archived | 제작·검토 상태. 여러 채널이 한 상태를 공유하지 않음 |
| 실행 | queued / running / waiting / partial / completed / failed / cancelled | 한 논리 작업의 진행 상태 |
| 배포 | pending → ready → submitting → uploaded/scheduled → published → verified | 대상별 외부 게시 상태 |
| 예외 | needs_auth / needs_review / retry_wait / unknown / verification_failed | 자동 진행이 멈추거나 조회가 필요한 이유 |

위 상태명은 계약 제안이다. `unknown`은 실패와 구별하고, 외부 게시가 발생했을 수 있음을 뜻한다. `cancelled`는 로컬 미실행 취소이며 이미 공개된 글을 삭제했다는 뜻이 아니다.

원격 예약을 취소·수정하는 기능은 지원하는 어댑터에서 별도 명시적 작업으로 수행하고, 로컬 예약 취소와 구별한다. 과거 예약 시각은 자동으로 즉시 공개로 바꾸지 않고 해당 작업의 기존 지연 정책을 적용한다. 기존에 준비 완료 후 즉시 공개하도록 정한 작업은 그 규칙을 보존한다.

### 영속 원장

설계자 제안은 표준 라이브러리 SQLite다. 원자적 상태 전환·중복 키·한도 예약을 하나의 트랜잭션에서 처리하기 위해 사용한다. 원문 Markdown·미디어는 파일로 유지하고 원장에는 경로·해시·상태를 저장한다.

핵심 기록은 jobs, triggers, runs, contents/revisions, deliveries, attempts, approvals, quota_reservations, events, incidents, metrics다. SQLite 파일은 로컬 USB256 볼륨의 `ax-console/data/operations.sqlite3`를 후보로 하되, 저널 모드는 파일시스템 잠금·내구성 시험 후 선택한다. 네트워크 공유 저장소는 사용하지 않는다. 대용량 이미지·영상은 DB에 넣지 않는다.

전환된 작업의 상태 기준은 SQLite 하나다. 기존 JSON은 가져오기 원본 또는 단방향 조회용 출력으로 한정하며 양방향 독립 갱신하지 않는다. 아직 전환하지 않은 legacy 작업은 기존 상태 저장소를 기준으로 하고 원장에는 관측 결과만 연결한다.

동시 쓰기는 짧은 트랜잭션과 단일 디스패처로 제한한다. 작업 실행·네트워크 대기 중 DB 트랜잭션을 열어 두지 않는다. 실행 중에는 lease와 heartbeat를 기록하되 lease 만료만으로 재게시하지 않는다. 복구 시 프로세스·잠금·외부 결과를 확인한다. USB 분리·DB 잠금·저장 실패는 새 공개 작업 중단과 사건 생성 대상으로 다룬다.

## 7. 트리거·실행자·중복 방지

각 작업은 `schedule_owner = launchd | console`을 하나만 가진다. 기존 launchd 일정은 유지하고 콘솔은 같은 일정을 중복 등록하지 않는다. 최종적으로 launchd는 시각에 실행 요청을 제출하고 워커가 실행한다. 기존 launchd와 콘솔이 같은 작업을 직접 실행하지 않도록 작업별 `execution_owner`를 한 곳에서 정한다.

전환 중에는 `legacy`와 `managed`를 혼용할 수 있지만 한 작업의 실행 주인은 하나다. shadow 모드는 요청·예정 대상·한도·잠금을 비교할 뿐 실제 게시나 실행 요청을 만들지 않는다. 대상 작업의 기존 직접 실행을 차단한 뒤에만 managed 경로를 켠다. Claude 작업도 새 원장에 실행 결과를 쓰는 호환 단계를 거쳐 점진 전환한다.

- 트리거 중복 키: 작업 ID + 회차(Asia/Seoul 시각·실행 유형). 생성 회차와 공개 확인 회차를 서로 다른 유형으로 구분한다.
- 배포 중복 키: 원본 콘텐츠 ID + 승인된 버전 + 대상 연결 + 의도된 게시 회차. 재시도는 같은 배포 ID를 사용한다.
- 제목은 보조 조회 근거이며 유일한 중복 키가 아니다. 게시 후 텍스트 해시·게시 ID·예약 시각 등과 함께 조회한다.
- 같은 콘텐츠의 변경 버전을 자동 신규 게시로 취급하지 않는다. 기존 게시 수정·재게시·후속편을 별도 의도로 구분한다.
- 수동 “다시 실행”도 같은 요청이면 기존 실행을 보여 준다. 새 게시를 의도한 재발행은 별도 확인·기록이 필요하다.

발행 요청 전 attempts에 대상·버전·시간을 기록한다. 응답의 게시 ID·URL을 먼저 영속화하고 후처리를 분리한다. 플랫폼이 지원하는 경우에만 원격 idempotency 키를 사용한다.

타임아웃·프로세스 종료로 결과가 불확실하면 `unknown`으로 보내고 대상 계정에서 최근 게시·예약 목록을 조회한다. 하나의 게시물과 충분히 일치하면 연결해 재개한다. 일치가 없다는 증거가 부족하거나 후보가 여러 개면 사람이 확인할 때까지 재전송하지 않는다. 제목만 일치한 글을 자동으로 소유하지 않는다.

## 8. 잠금·한도·예산·정지

기존 `axlock`을 잠금의 단일 기준으로 재사용한다. 프로필 별칭은 계정 잠금으로 정규화하며 외부에서 사람이 연 로그인 브라우저도 대기 원인으로 존중한다. 하위 프로세스에 넘기는 잠금 소유 정보는 상위 실행과 자원 범위를 확인하고 환경변수 존재만으로 다른 작업의 잠금을 건너뛰지 않는다.

공용 등록부의 자원 집합을 정렬해 획득 순서를 고정한다. 제작·음성·영상 렌더 같은 장시간 단계는 브라우저 잠금을 잡지 않는다. 교차 게시도 대상 배포별 잠금을 잡아 출발·도착 계정 잠금을 불필요하게 오래 함께 점유하지 않는다. 기존 스크립트가 여러 계정에 게시하는 동안은 필요한 전체 자원을 명시하고, 대상별 분해가 끝난 뒤 잠금 범위를 줄인다.

- 한도는 소유 계정이 아니라 실제 게시 대상 연결·플랫폼 할당량에 차감한다. 제작 예산은 원본 소유 계정에 귀속한다.
- 공용 API 프로젝트 한도와 계정별 편집상 발행량은 다른 자원이다. 기존 Blogger 한도와 실제 게시 목록을 초기 기준으로 보존한다.
- 원장에서 한도를 예약하고 성공 시 확정한다. 외부 결과 미확정 건은 중복 소비를 막기 위해 보수적으로 예약을 유지한다.
- 한도는 원격 게시 이력과 대조한다. 수동으로 게시한 글도 기존 한도 정책에 맞게 반영한다.
- 자동 승인 집계·AI 비용·미디어 크레딧은 계정별과 공용을 구분하고, 미확정 비용은 확인 전 0으로 처리하지 않는다.

전역 STOP은 진입 시·잠금 대기 중·잠금 획득 직후·공개 부작용 직전에 확인한다. STOP 설정과 신규 게시 시작 허가는 같은 공통 관문에서 순서를 직렬화한다. 시작 허가를 받은 원격 요청은 진행 중 작업으로 기록하고 이후 요청부터 차단한다. 실행 중인 업로드를 강제로 죽여 롤백됐다고 간주하지 않는다. 이미 외부 요청이 나간 작업은 결과 조회·기록을 계속하고 새 후속 게시를 시작하지 않는다. 재개해도 미처리 작업을 일괄 공개하지 않고 기존 회차·지연 정책에 따라 재평가한다.

계정·채널별 일시 중지도 도입하되 전역 STOP보다 우선할 수 없다. 불필요한 상태 알림 대신 실패·완료·인증 필요·의미 있는 변화만 알린다. 알림 실패는 원래 발행 결과를 실패로 뒤집지 않는다.

## 9. 현재 교차 게시 보존

| 기존 경로 | 보존할 동작 | 관리 방식 |
|---|---|---|
| 개인 숏츠 → 학과 TikTok | 기존 대기열, 공개 후 지연·간격, AI 고지 | 원본 게시와 연결한 대상 배포 |
| 개인 GeoAI 저녁 글 → 학과 Threads | 저녁 회차 조건·변환·매체 첨부 | 기존 트리거 조건을 규칙으로 옮김 |
| 학과 채용정보 → 개인 Tistory | 기존 글 변환·출처·실행 조건 | 채용 원본의 별도 대상 배포 |
| 개인 Tistory → 개인 네이버 | safeworking 대상·카테고리 매핑·출처 | 동일 계정 내 채널 배포 |

점검한 TikTok 대기열의 조건은 공개 예정 시각 기준 30분 뒤, 게시 사이 최소 3시간, 07:00 이상 23:00 미만 게시 창이다. 신규 실행기와 기존 대기열 중 한 곳만 이 지연을 계산해 두 번 더하지 않는다. 이는 현재 확인한 기준선이며 이행 때 최신 코드·설정·사용자 지시와 다시 대조한다.

대상 계정·콘텐츠 변환·회차·간격·태그·AI 고지·성공 조건을 이행 전후 대조한다. 현재 주석의 숫자보다 실제 설정과 사용자 지시가 우선이며 구현 시 최신 근거를 캡처한다. 꺼진 작업은 꺼진 상태를 보존한다. 한 경로의 게시 실패로 이미 성공한 원본을 재생성하거나 다시 게시하지 않는다.

기존 내부 대기열 추가와 새 배포 생성이 동시에 작동하지 않도록 경로별 `delivery_owner`도 하나로 둔다. 새 등록부에 보이지 않는 숨은 교차 게시 부작용이 있는 legacy 실행기는 분해 전까지 그 전체 동작을 계약에 명시한다.

## 10. 승인·제작·검토

기존 작업별 승인·자동 진행 수준은 초기 정책으로 이관하고 확대하지 않는다. 새 작업·알 수 없는 유형은 검토 대기에서 시작한다. 새 자동 승인 범위 확대는 정책 변경 이력과 사용자 결정을 요구한다.

원본·채널별 변환본·이미지·음성·영상·출처·수치 검토 결과를 콘텐츠 버전에 묶는다. 수식·숫자는 기존 calc-verifier, 출처는 source-reviewer 절차를 보존한다. 한국어 문체 정리와 기존 폰트·AI 고지·Remotion·디오라마 제작 지침도 유지한다. 현재 실행기와 지침이 다른 부분은 자동 전환하지 않고 해당 제작 이행 범위로 기록한다.

AI 에이전트는 초안·검토 제안과 구조화된 제작 산출물을 반환한다. 실제 발행 권한은 등록된 실행 컨텍스트를 검증하는 실행기에 둔다. 기존 Claude 작업이 직접 발행하는 구간은 legacy로 표시하고, 구조화된 결과·관리 발행기로 나누는 단계에서만 권한을 전환한다.

## 11. 폴더·데이터 이행

최종 논리 구조는 기존 최상위 폴더를 유지한다.

```text
common/
  shared/                  기존 잠금·경로·비밀·LLM 기반
  operations/              등록부 해석·실행 원장·상태·복구(제안)
  publishers/              계정 비선택 채널 어댑터(제안)
  remotion-shorts/          공용 영상 제작
  analytics/               계정 컨텍스트를 받는 수집·보고

dept/                      학과 정책·작업·콘텐츠·이력·출력
personal/                  개인 정책·작업·콘텐츠·이력·출력
ax-console/                통합 운영 화면과 로컬 실행 원장
site/                      홈페이지·접수 연동, 소유 계정 명시
```

위 신규 디렉터리명은 제안이며 이번 문서 작성으로 생성하지 않는다. 계정별 디렉터리에는 공용 게시 알고리즘을 복제하지 않고 정책·작업 정의·계정 전용 제작 로직을 둔다. 콘텐츠 소유 데이터는 계정별로 두되 중앙 원장의 참조로 조회한다. 실제 파일 경로는 계정 ID만으로 임의 생성하지 않고 검증된 저장소 기준 경로에서 결정한다.

이행 순서는 명시적 컨텍스트 → import 시 부작용 제거·공용 로직 추출 → 계정 전용 코드 이동 → 계정별 새 산출물 경로 → 과거 데이터 이관 → 구경로 의존 제거다. 초기에는 과거 원고·로그·이미지·실제 로그인 폴더를 물리 이동하지 않는다.

원래 실행 환경은 경로에 민감하므로 `.venv`를 이동·복사해 해결하지 않는다. 실행기에서 기존 환경 경로를 명시하고, 재현 가능한 환경을 별도로 준비·검증한 다음 전환한다. 루트 계산은 `common/shared/paths.py` 기준으로 통일한다.

호환 링크는 기존 호출자를 살리되, 어느 방향이 원본인지 목록으로 관리한다. 코드만 옮겨도 기본 config·profile이 학과로 넘어가는 링크는 그대로 새 실행 기본값으로 쓰지 않는다. launchd·Claude 지시문·콘솔·외부 스크립트·가상환경 참조가 새 계약을 쓰는 것을 확인한 후에만 옛 링크를 제거한다.

## 12. 단계별 이행과 종료 조건

아래는 설계 수준의 이행 단계이며 파일별 구현·시험 명령 계획은 설계 승인 후 작성한다.

| 단계 | 산출물 | 종료 조건 |
|---|---|---|
| 0. 기준선 고정 | 계정·연결·작업·교차게시·경로·비활성 상태 목록 | 등록부 37개와 plist 33개 차이를 각각 설명하고 실제 운영 상태와 구분 |
| 1. 등록부·컨텍스트 | 계정·대상·자격증명·지원기능·정책 계약 | 알 수 없는 계정·대상 불일치를 공개 요청 전에 차단 |
| 2. 실행·결과 원장 | 실행·배포·시도·승인·한도·사건 기록 | 응답 유실·재시작·동시 요청에서 중복 없는 복구 또는 명시적 확인 대기 |
| 3. 기존 실행기 연결 | 채널별 managed/legacy 상태·기능 행렬 | 실행 주인·교차게시 주인이 하나이며 기존 동작과 비교 일치 |
| 4. 구조 이행 | 공용 모듈·계정별 코드·설정·데이터 경계 | 개인 작업의 묵시적 학과 기본값·로그·프로필 참조 없음 |
| 5. 운영 순환 | 계정별 정책·공개 검증·성과·기획 연결 | 원본→모든 대상→공개검증→성과를 추적하고 계정별 예산·한도 적용 |

전체 흐름을 구축하되 활성화는 대상별로 나눈다. 기존 콘솔 연결 채널에서 계약을 검증한 다음 Tistory·개인 네이버·YouTube·Instagram·Threads·TikTok 순서를 실제 상태와 리스크에 맞춰 정한다. 이 순서는 신규 채널 운영 승인이나 기존 작업 중단을 뜻하지 않는다.

각 단계는 설정·상태 스냅샷, shadow 비교, 비발행 시험, 결과 검토, 대상별 전환을 거친다. `--dry`도 편집기 입력이나 외부 상태 변경을 할 수 있으므로 공개 효과 없는 순수 fixture 시험을 먼저 사용한다. 향후 로그인 브라우저를 여는 시험은 반드시 axlock으로 감싼다. 공개 시험·예약 생성은 따로 범위를 승인받는다.

## 13. 복구·이전·롤백

기존 JSON 상태는 읽기 전용으로 스냅샷하고, 원본 경로·해시·기존 ID를 보존한 매핑으로 가져온다. 과거에 완료됐다는 기록만 있는 건은 `legacy_recorded`로 표시하고 공개 검증 완료와 구별한다. 가져오기 재실행은 같은 기록을 중복 만들지 않아야 한다. 새 원장과 구상태에 둘 다 쓰는 기간은 두 시스템이 게시를 실행하는 기간과 다르다.

스케줄 전환은 대상 작업의 새 제출을 막고 진행 중 실행·잠금·unknown 결과를 정리한 뒤 수행한다. 기존 launchd·비활성 상태·환경·정책 스냅샷을 보존한다. DB 백업은 SQLite의 일관된 백업 방식으로 만들며 실행 중 파일 하나만 복사하는 방법을 쓰지 않는다. 복구 시험은 실제 게시를 하지 않는 사본에서 한다.

롤백은 코드·작업 실행 주인·경로 참조를 이전 버전으로 돌리되, 이미 게시된 외부 결과와 새 원장의 게시 ID를 삭제하지 않는다. 신규 원장에만 있는 성공·unknown·한도 예약을 기존 실행기에 중복 방지 자료로 전달할 수 없으면 해당 작업은 중지하고 정합성을 맞춘 뒤 재개한다. 과거 DB 스냅샷 복원으로 공개 이력을 잊어버리는 롤백은 금지한다.

## 14. 병렬 작업 경계

사용자 요청에 따라 독립 작업은 에이전트를 나눠 진행한다. 구현 단계에서의 후보 분할은 다음과 같다.

- 등록부·계정 경계 담당: 스키마·컨텍스트·대상 확인 계약.
- 실행·복구 담당: 원장·상태머신·중복 방지·한도.
- 채널 어댑터 담당: 합의된 계약으로 독립 채널을 연결.
- 구조·성과 담당: 공용 코드 정리·경로 이행 또는 성과 수집.

같은 파일·실제 브라우저·스케줄·원장을 여러 담당이 동시에 바꾸지 않는다. 먼저 계약을 고정한 다음 채널 어댑터를 병렬화한다. 프로필을 공유하는 시험·데이터 이관·스케줄 전환·최종 통합 검증은 직렬로 한다. 현재 이용 가능한 동시 에이전트 수 내에서 부모가 통합·검토를 맡는다.

## 15. 수락시험과 증거

| 검증 대상 | 필요한 시험·증거 |
|---|---|
| 계정 격리 | 잘못된 account/target/credential/meta 조합이 어댑터의 외부 게시 호출 전에 차단 |
| 교차 게시 유지 | 네 기존 경로의 대상·변환·회차·간격·활성 상태를 캡처한 fixture와 새 결과 일치 |
| 중복 요청 | launchd·콘솔 동시 요청, 회차 재실행, 수동 재시도에서 같은 논리 실행·배포를 참조 |
| 응답 유실 | 게시 성공 직후 응답 단절·프로세스 종료 시 재전송하지 않고 조회로 연결하거나 unknown 대기 |
| 부분 성공 | 원본·일부 채널 성공 후 다른 채널 실패 시 실패 대상만 재시도 |
| 승인 고정 | 본문·이미지·대상·일정 변경 시 기존 승인이 무조건 재사용되지 않음 |
| 예약·공개 구분 | YouTube 등 예약 완료를 공개·검증 완료로 오인하지 않음 |
| 한도·예산 | 동시 작업과 수동 게시·교차 게시가 대상별 발행량, 소유 계정 제작비, 공용 한도에 반영 |
| 정지·인증 | 잠금 대기 중 STOP, 인증 만료, 사람이 연 프로필에서 게시 없이 대기·중단·안내 |
| 영속 복구 | worker 재시작·lease 만료·USB 분리·DB 저장 실패·백업 복구에서 중복 공개 없음 |
| 폴더 이전 | 옛 경로·새 경로가 동일 계정·원본 ID·게시 이력으로 연결되고 기본값 혼입 없음 |
| 성과 순환 | 게시 ID 기준 metrics가 원본·대상 계정과 연결되고 기획에 동일 계정 인증 사용 |

시험은 로컬 상태/fixture·가짜 어댑터 → 외부 읽기 전용 → 비공개 시험 → 승인된 공개 범위 순으로 넓힌다. 이번 설계 단계에서 실행했다는 의미가 아니다. 운영 가동 완료 판정은 위 기능별 증거를 모은 뒤 별도로 한다.

## 16. 남긴 판단과 승인 범위

사용자 확정 사항은 계정별 채널 자동 운영 목표, 현재 교차 게시 유지, A 순서, 독립 작업의 최대한 병렬화다. 상세 기술과 신규 모듈명·SQLite·상태 계약·이행 단계는 설계자가 제안했으며 사용자가 이 상세 설계를 승인했다.

기존 정책을 보존하는 것을 초기값으로 삼아 자동 승인 확대와 신규 채널 개설은 별도 결정으로 남긴다. 어댑터별 최신 플랫폼 기능, 로그인 유효성, 실제 미설치 작업의 사유, 현재 발행량·비용은 구현 기준선 단계에서 확인할 운영 사실이며 이번 문서로 확정하지 않는다.

사용자는 “설계 승인, 실행 계획 작성”을 선택했다. [파일별 실행 계획](../plans/2026-10-30-account-channel-automation.md)에 병렬 담당·검증·롤백 작업을 정리했다. 운영 코드나 실제 발행은 이번 범위 밖으로 유지한다.

독립 검토 기록: 세 분야 병렬 조사 결과를 통합한 뒤, 사전 대화 없이 설계서만 전달받은 별도 검토 에이전트가 계획 수립 가능성을 확인했다. 필수 추가 질문이나 중대한 모순은 발견되지 않았다. 이 검토는 설계 문서의 완결성에 대한 것이며 실행·발행·복구 시험의 통과를 뜻하지 않는다.
