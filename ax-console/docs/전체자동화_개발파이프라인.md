# 전체 자동화 개발 파이프라인

AX 발행 콘솔을 **전체 자동화**까지 끌고 가기 위한 목표 구조, 단계별 로드맵, 개발·시험·배포 절차.
(2026-10-18 초안, 검토용)

---

## 1. "전체 자동화"의 뜻

사람이 하는 일을 다음 세 가지로 줄이는 것이다.

1. **정책 정하기**: 어떤 계정·채널·주제를 얼마나 자주, 어느 수준까지 자동으로 낼지
2. **예외 처리**: 로그인 재인증(비밀번호·2단계 인증), 에이전트가 "모름"으로 넘긴 사건
3. **가끔 점검**: 주간 요약을 보고 정책을 고침

나머지(기획 → 초안 → 검토 → 제작 → 예약 → 발행 → 성과 → 다음 기획, 실패 대응)는 시스템이 한다.
단, 사람 승인 단계는 없애는 것이 아니라 **채널·주제별로 "자동 승인 정책"으로 바꾼다**(§5).

## 3. 목표 구조

```
┌──────────────────────────── AX 발행 콘솔 (127.0.0.1:8700) ─────────────────────────────┐
│ 계정 연결 · 콘텐츠 · 작업 · 자동 작업 · 예약 · 장애 · 내부 브라우저 · 정책 · 설정           │
└───────────────┬──────────────────────────────────────────────────────────────────────┘
                │
        ┌───────▼────────┐   하나의 작업 대기열. 모든 실행(launchd 작업 포함)이 여기를 거친다
        │ 오케스트레이터 │   계정·채널·브라우저 프로필 잠금, 하루 한도, 재시도, 비상 정지
        └───┬───┬───┬────┘
            │   │   │
   ┌────────┘   │   └──────────────┐
   ▼            ▼                  ▼
에이전트      발행 어댑터          브라우저 서비스
기획·초안     API 채널: 블로거·     프로필별 크롬 1개를 관리
실패 대응     유튜브·X·티스토리?    콘솔 '내부 브라우저'로 화면 중계·조작
제작(④)      브라우저 채널: 네이버·  사람 로그인도 콘솔 안에서
성과 분석     인스타·스레드·틱톡
            │
            ▼
   데이터: 콘텐츠·작업·사건·성과·에이전트 기록 (ax-console/data)
```

### 바뀌는 핵심 세 가지

1. **오케스트레이터 한 곳**: 지금은 launchd 작업 25개와 콘솔 예약, Codex 자동화가 서로를 모른 채 돈다. 그래서 크롬 프로필이 겹치고 네이버 자동저장이 섞였다. 앞으로는 모든 실행이 대기열을 거치고, 같은 프로필·계정을 쓰는 작업은 차례로 돈다.
2. **브라우저 서비스 + 내부 브라우저** (§4): 바깥 크롬 창을 없앤다.
3. **자동 승인 정책** (§5): 사람이 매번 승인하던 것을 조건부 자동으로.

## 4. 브라우저 서비스와 콘솔 '내부 브라우저'

### 요구
- 작업할 때 바탕화면에 크롬 창이 뜨지 않는다.
- 진행 화면을 콘솔 안에서 실시간으로 본다.
- 로그인 재인증(카카오 비밀번호, 인스타 확인 코드 등)을 **콘솔 안의 브라우저 화면에서 직접** 한다.
- 같은 프로필을 두 작업이 동시에 열지 않는다.

### 방식 비교

| 방식 | 창이 뜨나 | 사이트 차단 위험 | 콘솔에서 보기·조작 | 판단 |
|---|---|---|---|---|
| A. 지금처럼 보이는 크롬 | 뜸 | 낮음 | 안 됨 | 버림 |
| B. 헤드리스 크롬(`--headless=new`) | 안 뜸 | 사이트마다 다름(네이버·인스타는 막힌 적이 있어 지금 꺼 둠) | CDP 화면 중계로 가능 | **사이트별 시험 후 기본값** |
| C. 보이는 크롬을 화면 밖에 띄움 + 화면 중계 | 안 보임(화면 밖) | 낮음 | CDP 화면 중계·입력 전달로 가능 | **B 가 막히는 사이트의 대비책** |

두 방식 모두 크롬 개발자 프로토콜(CDP)로 화면을 받아(`Page.startScreencast`) 콘솔에 띄우고, 콘솔에서 누른 클릭·키 입력을 크롬으로 보낸다(`Input.dispatchMouseEvent` / `dispatchKeyEvent`). 그러면 사용자 입장에서는 콘솔 안에 브라우저가 있는 것과 같다.

### 구성
- **프로필 등록부**: 프로필 7개(네이버, 티스토리, 인스타, 유튜브 학과·개인, 틱톡, insta-manual)를 계정·채널과 묶어 등록한다. 프로필 폴더는 옮기지 않는다(로그인 유지).
- **프로필 잠금**: 프로필마다 한 번에 하나의 작업만. 다른 작업은 대기열에서 기다린다. Codex 같은 바깥 도구도 이 잠금을 확인하게 안내한다.
- **세션 관리자**: 작업이 크롬을 요청하면 서비스가 띄우고 CDP 주소를 넘긴다. 기존 Selenium 코드는 `debuggerAddress` 로 붙기만 하면 되므로 발행 코드를 크게 고치지 않는다.
- **로그인 상태 점검**: 매일 한 번 프로필별로 로그인 여부를 확인(글쓰기 화면이 열리는지)해 콘솔 계정 연결에 표시. 풀렸으면 사람에게 "내부 브라우저에서 로그인" 버튼.
- **녹화**: 실패한 실행은 마지막 30초 화면을 저장해 실패 대응 에이전트가 본다.

### 옮기는 순서
네이버(가장 자주, 자동저장 문제 경험) → 티스토리(로그인 문제) → 인스타·스레드 → 틱톡 → 유튜브 커뮤니티 → 렌더링용(배너·프레임 캡처, 이미 헤드리스 가능).

## 5. 자동 승인 정책

| 수준 | 내용 | 사람 |
|---|---|---|
| L0 | 지금. 사람이 모든 콘텐츠를 승인 | 매번 |
| L1 | 자체 검토 통과(`[확인 필요]` 0, 근거 없음 0, 자극적 표현 0) + 시리즈·정형 글은 자동 승인 | 시리즈 밖 글만 |
| L2 | 계정·채널별 정책으로 자동 승인. 사람은 발행 뒤 24시간 안에 내릴 수 있음 | 사후 점검 |
| L3 | 기획까지 자동(주간 제안 중 정책에 맞는 것을 자동 선택) | 정책·예외만 |

**언제나 사람 승인으로 남기는 것**: 학과 공식 입장·입시 정보, 사건·사고 속보, 특정 기관·인물 언급, 처음 쓰는 주제 유형, 실패 대응 에이전트의 코드 수정안.

**안전장치**: 콘솔 첫 화면의 **비상 정지**(모든 자동 발행 즉시 멈춤), 채널별 하루 한도, 같은 주제 7일 안 반복 금지, 발행 후 자동 점검(주소 열림·본문 일치).

## 6. 개발 로드맵

순서는 **"실패해도 덜 위험한 것 → 공개 발행에 닿는 것"** 이다.

| 단계 | 이름 | 내용 | 끝난 모습 | 기간(가늠) |
|---|---|---|---|---|
| D1 | 오케스트레이터 | 작업 대기열, 계정·프로필 잠금, 비상 정지. 콘솔 예약과 launchd 작업을 대기열로 감싸기(스크립트 앞에 잠금 확인) | 프로필 겹침·자동저장 섞임이 구조적으로 사라짐 | **완료 (2026-10-18)** — `shared/axlock.py`, run_*.sh 24개 가드, 콘솔 실행 현황·비상 정지 |
| D2 | 실패 대응 1·2단계 | 감시기 + 장애 탭 + 원인 분석 에이전트(읽기 도구) | 실패가 30분 안에 원인과 함께 콘솔에 뜸 | **완료 (2026-10-18)** |
| D3 | 브라우저 서비스 + 내부 브라우저 | CDP 세션 관리, 화면 중계·입력, 프로필 등록부, 로그인 점검. 네이버부터 옮김 | 네이버 발행 때 바깥 창이 안 뜨고 콘솔에서 보임 | **1단계 완료 (2026-10-18)** — `app/browser_worker.py`, 콘솔 '브라우저' 탭, 로그인을 콘솔 안에서. 남음: 발행 스크립트를 이 서비스에 붙이기(debuggerAddress), 매일 로그인 점검 |
| D4 | 나머지 브라우저 채널 이전 | 티스토리·인스타·스레드·틱톡·유튜브 커뮤니티 | 바깥 크롬 창 0 | 2주 |
| D5 | 발행 어댑터 확장 | 인스타(카드 이미지 필요 → D6 와 함께), 스레드, 틱톡, 티스토리, 유튜브 | 모든 채널이 콘텐츠 파이프라인에서 자동 발행 가능 | 1~2주 |
| D6 | ④ 제작 | 카드 이미지(기존 카드 생성기), 디오라마 이미지(게이트웨이 이미지), Remotion 숏츠 | 초안에서 카드·영상까지 자동 생성 | 2~3주 |
| D7 | ⑦ 성과 | 발행 주소 기준 글 단위 성과 수집(유튜브 영상별, 서치콘솔 주소별, 블로거·네이버 조회) | 콘텐츠마다 성과가 붙음 | 1주 |
| D8 | 기획 에이전트 주간 제안 + 학습 | ⓪ 제안 칸, 반려 사유·수정 차이·성과 반영. 기술사 주제 넘겨받기(Codex 자동화 정리) | 매주 제안이 자동으로 올라옴 | 1~2주 |
| D9 | 실패 대응 3·4단계 | 안전 조치, 코드 수정안 | 알려진 실패는 사람 없이 정리 | 1주 |
| D10 | 자동 승인 L1 → L2 → L3 | 정책 화면, 사후 점검, 비상 정지 연습 | 사람은 정책·예외만 | 단계마다 2주 관찰 |
| D11 | 기존 launchd 작업 흡수 | 25개 작업을 콘텐츠 파이프라인·오케스트레이터 안으로 하나씩 이전 | 자동 작업이 모두 콘솔 안에서 같은 규칙으로 돈다 | 계속 |

D1·D2 는 공개 발행에 닿지 않으니 먼저 한다. D3·D4 는 로그인이 걸려 있어 사람이 함께 시험해야 한다.

## 7. 개발 절차 (모든 단계 공통)

### 7-1 작업 단위
- 단계마다 **설계 메모 → 구현 → 시험 → 배포 → 관찰** 순서. 설계 메모는 `docs/` 에 남긴다.
- 커밋은 기능 하나씩, 메시지에 "무엇을, 왜, 어떻게 확인했는지".
- 다른 에이전트(Codex, 다른 Claude 세션)와 같은 파일을 동시에 고치지 않는다. 큰 단계는 별도 작업 세션에서 하고 끝나면 이 저장소로 합친다.

### 7-2 시험 사다리 (위로 갈수록 실제에 가까움)

| 칸 | 방법 | 쓰는 곳 |
|---|---|---|
| 1 단위 | 파이썬 함수 시험(변환·파싱·정책 판정) | 모든 단계 |
| 2 재생 | 지난 로그·스크린샷·실패 기록으로 다시 돌려 같은 결론이 나오는지 | 실패 대응, 감시기 |
| 3 점검(dry) | 각 채널을 '게시 직전'까지 (지금 `--dry`) | 발행 어댑터, 브라우저 이전 |
| 4 시험 발행 | 개인 블로거 같은 낮은 위험 채널에 올리고 바로 비공개(10-18 에 한 방식) | 새 어댑터 첫 연결 |
| 5 그림자 운전 | 새 경로와 옛 경로를 함께 돌리되 새 경로는 점검만, 결과 비교 | launchd 작업 흡수, 자동 승인 |
| 6 실제 | 한 채널부터 켜고 1~2주 관찰 | 모든 단계 |

공개 발행(칸 4 이상)은 매번 사람이 시험 범위를 승인한다.

### 7-3 배포와 되돌리기
- 배포 = 커밋 후 콘솔 서버 재시작(`launchctl kickstart -k gui/$(id -u)/com.smuds.axconsole`).
- 되돌리기 = `git revert` 후 재시작. 설정(`config/*.json`)은 바꾸기 전 사본을 `data/config-history/` 에 남긴다.
- 새 기능은 설정 스위치를 끈 채로 배포하고, 시험이 끝나면 켠다(예: `incident.enabled`).

### 7-4 관찰
- 콘솔 장애 탭(D2 이후), 주간 요약(성과 + 실패 + 에이전트 사용량)
- 에이전트 사용량은 월 한도(지금 300만 토큰)와 함께 설정 탭에서 본다.

## 8. 위험

| 위험 | 대응 |
|---|---|
| 헤드리스를 막는 사이트 | 사이트별 시험, 막히면 화면 밖 보이는 크롬(방식 C) |
| 로그인 재인증이 자주 걸림(카카오·인스타) | 내부 브라우저에서 사람이 바로 로그인, 로그인 상태 매일 점검 |
| 자동 승인 뒤 잘못된 글 | L1 부터 천천히, 사후 내리기 24시간, 비상 정지 |
