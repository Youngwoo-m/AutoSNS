# 계정별 운영 웹

신규 웹은 기존 8700 콘솔과 별도 프로세스로 실행한다. 기존 자동 작업·교차 게시 경로의 실행 주인은 그대로 유지한다.

## 조회 화면 실행

저장소 루트에서 실제 운영 자료의 위치를 지정한다.

```bash
AX_SOURCE_ROOT=/Volumes/USB256/devAPP/AutoSNS \
AX_AUTH_DIR=/Volumes/USB256/devAPP/AutoSNS/ax-console/data/auth \
AX_LAUNCHAGENTS_DIR="$HOME/Library/LaunchAgents" \
AX_PORT=8767 \
python3 ax-console/app/web_server.py
```

`http://127.0.0.1:8767`에 기존 콘솔 비밀번호로 로그인한다. 새 웹은 세션·쿠키를 별도로 저장하므로 첫 접속 때 다시 로그인한다. 비밀번호가 변경되면 새 웹의 이전 세션도 무효화한다.

계정 필터는 관련 원본과 대상 배포를 고른다. 개인 원본이 학과 채널로 교차 게시되면 양쪽 보기에서 원본을 찾을 수 있다. 누적 게시 기록·원격 예약 기록·공개 내용 검증은 다른 상태다. 인증 미확인은 로그인 실패 또는 연결 성공을 뜻하지 않는다.

## 관리 저장소를 사용하는 개발 모드

별도 저장 루트를 명시했을 때 새 기획과 로컬 배포 계획 저장을 제공한다. 기존 운영 자료와 겹치지 않는 위치를 사용한다.

```bash
AX_SOURCE_ROOT=/Volumes/USB256/devAPP/AutoSNS \
AX_AUTH_DIR=/Volumes/USB256/devAPP/AutoSNS/ax-console/data/auth \
AX_WORKSPACE_ROOT="$PWD/ax-console/data/managed-workspace" \
AX_PORT=8769 \
python3 ax-console/app/web_server.py
```

관리 저장 루트에는 `operations.sqlite3`와 개인·학과별 불변 콘텐츠 파일이 생긴다. 기존 운영 JSON은 편집하지 않는다. 아직 전환하지 않은 기존 작업의 결과와 새 관리 콘텐츠는 출처를 구분해서 표시한다.

새 기획에서 원본 소유 계정을 직접 고른다. 대상별 변환본에는 별도의 게시 대상 계정을 고른다. 원본 소유권은 생성 뒤 바꾸지 않는다. 수정·자산 추가는 새 버전을 만들고 과거 버전을 유지한다. 두 창에서 수정하면 충돌을 알리므로 초안을 보존한 채 최신 버전을 확인한다.

## 로컬 배포 계획·계획 승인

관리 원본 상세의 ‘배포 계획·계획 승인’에서 등록 연결·일정 슬롯·예정 시각·허용 범위·공개 옵션을 고르고 미리보기 뒤 저장한다. 연결은 도구 사용 선호와 별개다. 대상 ID가 미확인이면 초안만 저장하고 승인할 수 없다. 대상 ID 확인은 실제 로그인이나 발행 성공을 뜻하지 않는다.

계획 승인은 실제 발행 승인과 구분한다. 허용 시간 범위 안 이동은 승인을 유지할 수 있으며 범위 밖 이동은 재검토로 전환한다. 변경할 때마다 먼저 일정 영향을 확인한다. 로컬 계획 취소는 원격 예약 취소·게시물 삭제가 아니다.

배포 초안을 작성 중이면 원본 버전을 바꾸는 저장·자산 등록을 막는다. 필요한 경우 ‘입력 버리고 계획 다시 불러오기’를 명시적으로 선택한다. 승인 메모와 일정 입력은 서로의 저장으로 지워지지 않는다.

교차 발행 화면은 등록 규칙·자동 작업 관측·배포 계획/기록을 구분한다. 출처별 개수는 합산하지 않으며 ‘설정상 활성’도 실제 가동·인증 확인을 의미하지 않는다. 현재 등록 규칙의 실행 주인은 기존 발행기다.

수동 검토 기록은 선택한 버전과 해시에 귀속된다. 독립 검산·출처 검토 도구의 실행 결과 또는 발행 승인으로 취급하지 않는다. 원문·자산을 수정하면 이전 버전의 검토를 새 버전으로 복사하지 않는다.

‘채널·계정’의 계정별 도구 설정은 사용 선호와 대상 이름을 저장한다. 설정을 켜도 기존 자동 작업이나 실제 발행을 활성화하지 않는다. Metricool·vidIQ의 Codex 설치와 웹의 실행 연결은 별개다. 인스타그램·스레드·X·티스토리·페이스북은 연결 상태를 확인하기 전까지 미확인으로 남는다.

## 검증 범위와 후속 단계

기본 개발 모드는 실제 발행·AI 제작 실행 정책이 비활성이다. 등록 서비스를 명시 주입하는 격리 시험과 실제 운영 수락은 구분한다. Mac·휴대폰 외부 접속과 실계정 공개 검증·운영 전환은 후속 필수 수락 대상이다. 현재 서버는 localhost만 허용한다. 현재 관리 원장은 v3이며 명시 초기화 전에 DB와 콘텐츠 파일을 함께 백업한다.

저장 시험은 임시 데이터로 수행한다. 운영 자료를 개발 fixture로 쓰지 않는다.

```bash
python3 -m unittest discover -s tests -p 'test_*.py'
node --test tests/*.mjs
```

## 관리 실행·문제 복구

‘오늘 운영’ 위쪽의 관리 실행 현황은 기존 발행 관측·로컬 계획과 별도 집계다. 공개 전 예약은 ‘예약됨 · 공개 확인 전’, 응답 유실은 ‘게시 여부 불확실’로 표시한다. ‘장애·설정’의 문제·복구에서 해당 원본 제목을 눌러 시도 기록과 안전하게 정제한 확인 근거를 본다.

로컬 실행 취소는 검토 메모를 적어 기록한다. 고급 JSON을 입력하지 않아도 된다. 이 취소는 원격 게시 여부의 확정이 아니므로 원격 결과가 불확실한 기록은 문제 목록에 남는다. 기존 게시물 연결은 서버의 채널 조회, 미게시 확인은 이전 프로세스·잠금의 독립 확인을 요구한다. 현재 기본 서버에는 실제 채널 어댑터·관측기가 등록되지 않아 해당 동작의 차단 이유를 표시한다.

같은 원본의 여러 대상에서 실패한 배포만 선택해 동일 실행을 재개한다. 게시 여부가 불확실한 대상은 재전송하지 않는다. 원격 결과가 확인되지 않은 형제 채널이 있어도, 독립적으로 미제출이 확정된 대상은 별도 근거와 승인 조건을 갖춰 재개할 수 있다. 실제 실행 정책은 기본 비활성이며 화면에서 활성화하지 않는다.

‘채널·계정’의 관리 실행 제어는 전체 관리 작업·개인/학과 계정·등록 채널 범위로 중지/재개한다. 변경 사유와 최신 버전을 기록한다. 기존 전역 STOP은 관측 전용이며, 이 관리 중지는 기존 자동 작업·launchd에 적용되지 않는다. 재개는 밀린 회차의 일괄 등록을 뜻하지 않는다.

두 창에서 변경하면 입력을 보존하고 충돌을 알린다. ‘내 입력을 유지하고 최신 버전 확인’ 또는 ‘제어 최신 버전 확인’으로 새 상태를 본 뒤 근거를 다시 검토한다. 같은 요청의 응답이 유실되면 동일 요청키로 결과를 재확인하며, 성공한 뒤 새 조회는 별도 요청으로 처리한다.

4단계 시작은 관리 DB v2를 v3로 명시 이행한다. 업데이트 전 소유 개발 서버를 종료하고 SQLite backup API와 콘텐츠 파일을 함께 백업한다. 실제 채널 제출·제작 실행·성과 수집·외부 접속·기존 스케줄 전환은 후속 수락 대상이다.


## 5단계 성과와 기획제안

‘성과’는 저장한 검증 배포 관측과 과거 보고 자료를 구분한다. 실제0·오류·미지원·미수집을 따로 표시하고 관측·수집·파일 수정 시각 및 정의·누적/기간 기준을 상세에서 확인한다. 같은 원본이 다른 계정 채널에 배포되면 양쪽 관련 보기에서 찾을 수 있지만 채널 실적은 대상 계정에 귀속한다. 예산 기록이 있어도 실제 과금 자료가 없으면 제작비는 미확인이다.

‘가져오기 미리보기’는 운영 원본의9개 허용 통계 파일을 읽기만 한다. 현재 계정 필터와 관계없이 전체 계정의 과거자료를 확인한다. 명시 저장 전에는 관리 DB에 넣지 않는다. 저장 직전 원본이 바뀌면 미리보기·요청을 보존하고 충돌을 알린다. 기존 요청을 버리고 새 미리보기를 확인한 뒤 저장한다. 응답만 유실됐으면 같은 요청으로 원래 결과를 회수한다. source의 원본 파일은 고치지 않는다.

원본 계정을 확인하지 못한 과거 통계를 임의 개인/학과 원본으로 만들지 않는다. 등록 대상도 확인되지 않으면 전체 보기의 미귀속 자료로 남는다. 파일 행수·게시목록·과거 보고값은 오늘 공개 실적이나 현재 검증 성과가 아니다.

관측을 선택해 계정·제목·메모와 함께 ‘기획제안 초안 저장’을 누른다. 제안은 콘텐츠 기획의 ‘성과 근거 기획제안 초안’에도 나타난다. 이 동작은 원고 자동 생성·모델 호출·발행 승인을 하지 않는다. 원고 작성은 기존 ‘새 기획’에서 명시적으로 시작한다.

현재 실제 수집기/공식 인증 연결은 미등록이고 화면 새로고침으로 외부 SNS/API를 호출하지 않는다. Instagram·Threads·X·Tistory·Facebook도 구현·권한·수집 상태를 별도로 표시한다.

계정 경로 보고서는 `PYTHONDONTWRITEBYTECODE=1 python3 -m common.tools.audit_account_paths --help`로 사용법을 확인한다. 실제 move·링크 제거·키/프로필/.venv 이동은 제공하지 않는다. 보고서는 운영/source/code/managed 밖 새 파일로만 쓴다. 자세한 경계는 `docs/migrations/account-paths.md`를 따른다.

인증이 만료되면 ‘새 창에서 다시 로그인’을 연다. 로그인한 뒤 원래 작성 화면으로 돌아와 ‘로그인 완료 후 재조회’를 누르고 기존 저장 버튼으로 같은 요청을 재시도한다. 입력·선택·미리보기·요청키는 원래 문서에 보존된다. 작성 중 이탈 안내를 무시하고 탭을 강제 종료하면 복원되지 않으므로 원래 창을 유지한다.

색인 수·팔로워·구독자·클릭률 등 저장된 지표도 각각의 이름·단위로 표시한다. 단위가 확인되지 않은 비율은 보고값 그대로이며 임의 퍼센트 변환을 하지 않는다. 알 수 없는 수치는 상세에서 원래 이름/값을 확인한다. 정의가 다르거나 합산 근거가 없는 비율·평균·고유 수치는 개별 근거로 남는다. 새 수집 시도는 같은 결과여도 별도 이력이고 같은 시도 재전송만 동일 관측으로 처리한다.

5단계 반영 시 기존 운영 원장v3와 콘텐츠를 백업하고 별도 성과 DB만 초기화했다. 기존 통계는 ‘가져오기 미리보기’에서 확인한 뒤 사용자가 명시 저장한다. 백업을 되돌릴 때는 업데이트 이후 추가된 성과·제안·요청 receipt를 먼저 보존하며 기존 원장만 덮어쓰지 않는다. 관리 웹8769와 같은 정적 화면을 쓰는 읽기 전용8767을 함께 갱신했다. 새 웹의 실제 수집·발행과 기존 자동 작업의 새 원장 전환·물리 이동은 아직 비활성이다. 원래 자동 작업의 활성 상태는 유지한다.

## 6A 제작 요청·별도 발행 승인 — 정적 화면 배포와 운영 권한 구분

6A 코드 최종 재검토와 새 정적 화면 배포를 마쳤다. 실제8769에서 기술사 메뉴·건축 필터·실자료 표시를 확인했으며 기본 실행 정책과 실제 발행 서비스는 비활성/미주입이다. 병행 툴킷의 최신 전체 검증은 대기다. 화면의 연결 이름이나 제작 완료 표시가 실제 계정 인증·발행·운영 전환 완료를 뜻하지 않는다. [6A 수락 현황](../../docs/audits/2026-10-30-web-phase6a-acceptance.md)에서 확인한 범위와 미실행 항목을 본다.

관리 원고의 제작 요청은 선택한 원본 버전과 등록 작업에 결속된다. 같은 요청의 응답만 유실됐으면 같은 요청키로 결과를 다시 조회한다. 원고를 수정한 뒤에는 바뀐 버전을 별도 제작 요청으로 선택한다. 개인 구독-only 작업의 제작·검토를 다른 유료 API나 학교 API로 바꾸지 않는다. 제작 완료와 검토 완료는 발행 허가가 아니다.

발행은 등록된 실행의 대상 읽기 점검 → 발행 의도 확인 → 별도 발행 승인 순서로 진행한다. 원본 소유 계정과 실제 대상 계정이 다르면 양쪽을 확인한다. 대상 읽기 점검에서 불변 대상 ID·로그인이 확인되지 않으면 승인으로 넘기지 않는다. 계획 승인·제작 완료·운영 활성과 별도 발행 승인은 서로 다르다. 현재 기본 서버는 비활성/미등록 사유를 보여 주며 화면에서 운영 정책을 켜지 않는다.

상태를 다시 조회해 업로드·예약·공개·내용 검증을 구분한다. 예약은 공개 전이며 후처리 대기 표시도 완료가 아니다. 썸네일·재생목록·댓글·자막·예약 공개 전환·TikTok은 각각의 승인과 완료 근거가 필요하다. 실제 원격 매체를 검증하지 못하면 pending/unsupported를 유지한다.

‘게시 여부 불확실’은 자동 재발행으로 해결하지 않는다. 원장을 다시 열고 먼저 원격 조회로 기존 결과를 찾는다. 성공한 형제 채널과 원본 제작을 다시 실행하지 않으며, 미제출이 독립적으로 확정된 실패 대상만 재개한다. 이전 DB로 덮어쓴 뒤 기존 작업을 다시 켜면 새 원격 이력을 잊을 수 있으므로 [전환·복구 절차](../../docs/runbooks/account-operations-cutover.md)를 따른다.

기존 23개 교차 경로는 legacy owner로 유지한다. news.tiktok의 비활성과 나머지 미확인 상태를 임의로 켜지 않는다. 6A의 기존 TikTok 순수 큐 fixture 검증은 관리 TikTok 실행기의 운영 수락이 아니다. 관리 TikTok과 전체 경로 전환은 6B 필수 잔여다.

실제 구독 실행·독립 검산/출처 검토·출처 응답 bytes·음성·영상/글꼴/장면 품질·PDF 안전 파싱과 페이지 확인은 별도 수락한다. 기본 PDF safe parser가 없으면 PDF 필수 작업은 차단 상태를 유지한다. 실제 계정 로그인·발행·후처리·백업 복원·6B–6D·Mac/휴대폰 외부 접속은 아직 완료하지 않았다. 정적 배포 전 quiesced backup과 DB 보존 대조는 수행했으나 실제 복원 시험과는 다르다. 외부 접속 요구는 localhost 시험으로 대체하지 않는다.

현재 시험 결과는 기존 Pillow Python3.12 전체872개 통과, 이전 전체 Node195개와 이후 집중20개 통과다. 이를 최신 전체 Node 성공으로 합치지 않으며 현재 evidence의 offline-ready=false는 최종 전체 검증 대기를 뜻한다. production-ready=false는 실인증·실발행·복구·legacy 전환 증거가 아직 없다는 뜻이다. [결정·보류 기록](../../docs/audits/2026-10-31-phase6a-rulings.md)에서6A 범위와 후속 필수 작업을 확인한다. 원래 계획 작업공간은 아직 참조가 남아 있어 삭제하지 않았다.
